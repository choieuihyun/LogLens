# LogLens

**안드로이드 앱 로그를 정해진 형식으로 찍게 만드는 라이브러리 + 그 형식을 읽어서 분석해 주는 뷰어.**

로그가 지저분하면 아무리 좋은 뷰어를 써도 지저분하게 보입니다. 그래서 이 프로젝트는
뷰어보다 **"로그를 정해진 형식으로 찍게 만드는 쪽"**에 더 무게를 뒀습니다.
뷰어는 그 형식을 활용해서 필터링하고 집계하는 쪽이고요.

```
[앱] --형식에 맞는 로그--> [logcat 버퍼]
  (A) 로깅 라이브러리          │ adb
                               ▼
                     [ (B) 뷰어 / 분석기 ]
```

두 컴포넌트는 서로의 코드를 전혀 참조하지 않습니다. 공유하는 건 가운데의
**로그 한 줄 형식**뿐입니다.

📄 **문서** — [동작 원리·아키텍처](docs/ARCHITECTURE.md) · [로그 형식 정의](docs/RECORD_FORMAT.md) ·
[구현 결정 기록](docs/DECISIONS.md) · [설계 초안(기획서)](기획서.md) · [문서 안내](docs/README.md)

## 30초 만에 보기

기기도, adb도, 파이썬 패키지 설치도 필요 없습니다.

```bash
make viewer     # 가짜 로그를 만들어서 뷰어 실행 → http://127.0.0.1:8420
```

실제 라이브러리가 로그를 찍는 걸 보려면:

```bash
make demo       # 진짜 라이브러리 → 파일 → 뷰어  (전 구간 연결)
make emit       # 로그가 어떤 모양으로 찍히는지 터미널에서 확인
make test       # 전체 검증 (뷰어 + 라이브러리 + 양쪽 대조)
make aar        # 배포용 .aar 생성
```

## 로그 한 줄의 형식

```
<레벨>/<접두사>_<도메인>: evt=<이벤트> 키=값 키=값 | <자유 메시지>
```

```
2026-08-12 11:41:24.931 I/APP_AUTH: evt=LOGIN_OK flowId=f9254 uid=668 | 로그인 성공
2026-08-12 11:41:24.937 E/APP_NET: evt=REQUEST_FAIL host=api.example.test code=500 err=ConnectException:timeout
2026-08-12 11:41:24.930 I/APP_AUTH: evt=TOKEN_ISSUE flowId=f9254 token=*** expiresIn=3600 authType=oauth2
```

마지막 줄을 보면 `token`은 `***`로 가려졌는데 `authType`은 그대로입니다.
민감한 값을 가릴 때 **키 이름이 정확히 일치할 때만** 가리기 때문입니다.
`auth`가 들어간 키를 전부 가리는 식으로 만들면 `authType`처럼 멀쩡한 필드까지
안 보이게 되고, 그러면 개발자가 마스킹을 우회하기 시작합니다.

### 반드시 지켜야 하는 규칙 네 가지

- **태그는 `<접두사>_<도메인>`** — 도메인 이름을 그대로 logcat 태그로 씁니다.
  그래야 `adb logcat -s APP_AUTH:*` 같은 명령이 곧바로 도메인 필터가 됩니다.
- **로그 한 줄이 레코드 하나** — 여러 줄로 쪼개지 않습니다. logcat은 한 줄이
  4KB 근처를 넘으면 알아서 자르기 때문에, 우리가 먼저 잘라 두고 `...[cut]`을 붙입니다.
- **값에는 공백, `|`, 줄바꿈이 들어가지 않습니다** — 라이브러리가 알아서 치환합니다.
- **파서는 어떤 입력에도 예외를 던지지 않습니다** — 형식에 안 맞는 줄은
  버리는 게 아니라 등급을 낮춰서 보여줍니다.

## (A) 로깅 라이브러리

```kotlin
// 앱 시작할 때 한 줄
LogLensAndroid.install(this)

// 실제 호출부 — Kotlin
LogLens.i(AppDomain.AUTH, "LOGIN_OK", "uid" to uid, "msg" to "로그인 성공")
LogLens.e(AppDomain.NET, "SOCKET_FAIL", e, "host" to host)
LogLens.d(AppDomain.CHAT, "ROOM_ENTER")
```

**자바에서도 그대로 씁니다.** 라이브러리는 Kotlin 이지만 자바용 API 를 따로 냅니다.

```java
LogLens.i(AppDomainJava.AUTH, "LOGIN_OK", "uid", uid, "msg", "로그인 성공");
LogLens.e(AppDomainJava.NET, "SOCKET_FAIL", e, "host", host);
```

Kotlin 쪽은 `"uid" to uid` 라서 **키-값 짝이 컴파일 시점에 보장**됩니다 — 인자 개수를
홀수로 쓰는 실수 자체가 불가능합니다. 자바에는 `to` 같은 문법이 없어서, 같은 API 를
쓰려면 필드마다 `new Pair<>()` 를 써야 합니다. 자바가 대부분인 프로젝트에서는 마찰이
크기 때문에 기존 가변 인자 형태를 그대로 남겨 뒀습니다.

### 도메인 목록은 앱이 직접 정합니다

이게 "어느 프로젝트에나 붙는다"의 핵심입니다. 도메인 목록은 프로젝트마다 다른데,
라이브러리 안에 enum으로 박아 넣으면 그 순간 다른 프로젝트에서 못 씁니다.

```kotlin
// 라이브러리 쪽 — 도메인이 뭔지 모릅니다
fun interface LogDomain { fun tag(): String }

// 앱 쪽 — 자기 도메인을 정의합니다
enum class AppDomain : LogDomain {
    AUTH, CHAT, NET, FILE_XFER;
    override fun tag() = "APP_$name"
}
```

자바 프로젝트용 예시도 `lib/sample-domains` 에 같이 들어 있습니다
(`AppDomainJava.java`). 둘 중 맞는 걸 복사해 쓰면 됩니다.

### 구성

| 모듈 | 내용 | 필요한 것 |
|---|---|---|
| `lib/core` | `LogLens`(호출부가 쓰는 진입점), 포매터, 값 정리, 마스킹, 길이 자르기, 파일 저장 | Kotlin stdlib 만 |
| `lib/android` | logcat 출력, 앱 초기화 도우미 | Android |
| `lib/sample-domains` | 도메인 정의 예시 (Kotlin + Java) — 배포하지 않습니다 | core |

`core`가 안드로이드를 전혀 참조하지 않는 건 의도한 겁니다. 그래야 일반 JVM에서
바로 테스트할 수 있고, 뷰어 파서와 서로 대조하는 검증도 돌릴 수 있습니다.

### 붙이는 법

```bash
make aar    # → lib/android/build/outputs/aar/loglens-release.aar  (37KB)
```

`.aar` 하나에 core 까지 전부 들어 있습니다. 앱의 `libs/` 에 넣고 gradle 에 한 줄
추가하면 됩니다. Kotlin stdlib 외에 다른 의존성은 없습니다.

### 호출부가 신경 쓰지 않아도 되는 것들

- **개인정보** — `token`, `password`, `ssn` 같은 키는 라이브러리가 알아서 `***`로 바꿉니다
- **릴리스 빌드에서 V/D 로그** — 문자열을 조립하기도 전에 걸러냅니다.
  `init()`을 호출하기 전 기본값은 "디버그 아님"이라, 초기화를 깜빡해도 로그가 새지 않습니다
- **너무 긴 값** — 글자 단위로 잘라내고 `...[cut]`을 붙입니다.
  바이트 단위로 자르면 한글이나 이모지가 깨지는데, 그걸 피합니다
- **출력 중 예외** — 삼킵니다. 로그 때문에 앱이 죽으면 안 되니까요

## (B) 뷰어 / 분석기

### 브라우저는 USB를 못 봅니다 → 중간에 로컬 프로그램을 둡니다

```
[기기] --adb logcat--> [로컬 서버가 읽고 파싱] --SSE--> [브라우저 화면]
```

브라우저 보안 정책 때문에 웹페이지에서 USB나 adb에 직접 접근할 수 없습니다.
그래서 PC에서 도는 작은 파이썬 프로그램이 adb를 대신 실행해서 읽고, 그 결과를
브라우저로 밀어줍니다. Electron 같은 걸 쓰지 않아도 되고, 파이썬 표준 라이브러리만
쓰기 때문에 설치할 패키지도 없습니다.

### 기능

- **도메인 탭** — 클릭 한 번으로 필터링. 아직 라이브러리를 안 쓰는 예전 태그도
  정규식으로 지정해서 같은 탭에 모아 보여줍니다
- **레벨 / 검색 / 정규식 필터**
- **대상 앱만 보기** — `--package`를 주면 그 앱의 프로세스 ID를 찾아내서
  "이 앱만" 토글이 생깁니다. 앱을 재시작해서 ID가 바뀌어도 따라갑니다.
  단, 이슈를 클릭해서 보는 중에는 이 필터가 꺼집니다 — ANR은 앱이 아니라
  시스템(`ActivityManager`)이 찍기 때문에, 앱 ID로 거르면 방금 누른 이슈가 사라집니다
- **이슈 목록** — 크래시(예외 클래스별) / ANR / 네이티브 크래시 / 형식에 맞는 에러 로그를
  자동으로 묶어서 개수를 셉니다. 클릭하면 그 이슈만 필터링됩니다
- **분석 화면** — 성공률, 실패 사유 분포, 단계별 이탈, 도메인·이벤트 빈도.
  로그가 형식을 지켜야만 가능한 기능입니다. 일반 logcat 뷰어는 문자열밖에 없어서
  이걸 못 합니다

### 프로젝트마다 설정 파일로 맞춥니다

탭 목록도 이슈 규칙도 코드에 없습니다. [`config.json`](viewer/examples/sample-app.json)
([스키마](viewer/config.schema.json))만 바꿔 끼우면 됩니다.

```bash
loglens --source adb --package com.your.app --config your-app.json
loglens --source file --file dump.log --follow     # 저장해 둔 로그 재생
loglens --source synth                             # 기기 없이 가짜 로그로 데모
```

### 설정 파일은 자동으로 만들어 줍니다

아직 라이브러리를 안 쓰는 프로젝트에 "도메인 목록을 적어라"고 하면 아무도 안 씁니다.
뭘 적어야 할지 모르니까요. 그래서 실제 로그를 조금 읽어서 초안을 만들어 줍니다.

```bash
loglens --source adb --package com.your.app --init your-app.json
```

기기의 최근 logcat을 읽어서, **그 앱이 찍은 태그만** 골라내고 이름이 비슷한 것끼리
묶어서 탭 초안을 만듭니다 (`Chats`와 `ChatListFragment`는 한 탭으로).
이미 라이브러리를 쓰는 도메인이 있으면 그건 도메인 탭으로, 아직인 것은
예전 태그 패턴 탭으로 들어갑니다.

> **태그 이름과 개수만 읽습니다.** 로그 내용은 집계에도 결과물에도 쓰지 않습니다
> (테스트로 막아 뒀습니다).

처음 붙일 때 전체 순서는 [아키텍처 문서 §10](docs/ARCHITECTURE.md) 참고.

### 로그를 어디서 읽을지 고를 수 있습니다

`adb`(실제 기기) / `file`(저장된 로그) / `synth`(가짜 로그 생성)가 같은 인터페이스
뒤에 있습니다. 덕분에 기기 없이도 뷰어를 개발하고 테스트하고 시연할 수 있습니다.
기기가 잠들거나 USB가 빠져서 스트림이 끊기면 다시 붙는 처리도 adb 쪽에만 들어 있어서,
나머지 코드는 끊김을 신경 쓰지 않습니다.

## 이 도구가 요구하는 것 — 솔직하게

**분석 기능은 로그가 형식을 지킬 때만 동작합니다.** 이건 결함이 아니라 전제입니다.
다만 그 전제를 흐리지 않고 적어 둡니다.

| 기능 | 필요한 것 | 앱을 안 고쳐도? |
|---|---|:--:|
| 레벨 · 검색 · 정규식 필터 | 없음 | ✅ |
| 앱만 보기, 도메인 탭 | 없음 | ✅ |
| 크래시 · ANR · 네이티브 이슈 묶기 | 없음 — 시스템 로그를 읽습니다 | ✅ |
| 도메인 / 이벤트 빈도 | 형식에 맞는 로그 | ❌ |
| **성공률** | 이벤트 이름을 `_OK` / `_FAIL`로 통일 | ❌ |
| **실패 사유 분포** | 실패 로그에 `reason=` 또는 `err=` | ❌ |
| **단계별 이탈** | 흐름 전체에 `flowId=` + 설정에 단계 정의 | ❌ |

위 세 줄은 앱을 안 고쳐도 되지만, 솔직히 그것만으로는 Android Studio Logcat과
크게 다르지 않습니다. **아래 네 줄이 이 도구를 만든 이유이고, 전부 형식에 의존합니다.**

### 언제부터 쓸모가 있나

초안에는 "호출부 한 곳만 바꿔도 가치가 있다"고 적었는데, 실제로는 그보다 늦습니다.
한 줄 바꾸면 색깔 있는 칩 하나가 생기는 정도입니다. 성공률 차트는 성공과 실패
이벤트가 **짝으로** 있어야 나오고, 단계별 이탈은 흐름 **전체**에 `flowId`가 있어야 나옵니다.

**실질적인 최소 단위는 호출부 한 곳이 아니라 "흐름 하나 전체"입니다.**
로그인이든 메시지 전송이든, 시작·분기·끝이 다 기록된 흐름 하나요.
거기서 처음으로 일반 뷰어가 못 하는 화면이 나옵니다.

### 그래서 이건 무슨 도구인가

지저분한 로그를 알아서 정리해 주는 도구가 아닙니다.
**형식을 지키면 그만큼 돌려받게 만드는 도구**입니다. 형식을 안 지킨 로그도
사라지지는 않고 그냥 분석에서만 빠집니다. 이 차이가 형식을 지킬 이유가 됩니다.

OpenTelemetry나 Sentry 같은 도구도 성질이 같습니다. 넣은 만큼 나옵니다.

> 이 의존을 줄이는 방법 두 가지 — 뷰어 쪽에서 예전 로그를 정규식으로 뜯어내는 것,
> 그리고 기존 `Log.d` 호출을 자동 변환하는 도구 — 는
> [DECISIONS.md D20](docs/DECISIONS.md)에 적어 뒀습니다. 아직 안 만들었습니다.

## 양쪽 대조 검증

직접 손으로 쓴 테스트 데이터에는 **같은 오해가 양쪽에 들어갈 수 있습니다.**
제가 형식을 잘못 이해한 채로 테스트 데이터를 만들면 테스트는 통과합니다.
그래서 진짜 검증은 이렇게 합니다:

```
Kotlin 라이브러리가 만든 줄  →  Python 파서로 읽기  →  필드가 같은지 비교
```

```bash
make roundtrip
# roundtrip: 28 passed, 0 failed  (EXACT 24, TRUNC 4)
```

기대값은 라이브러리 출력을 되읽어서 만들지 않고, 입력값에서 따로 계산합니다.
그래야 비교에 의미가 있습니다. 이 검사가 실제로 문제를 잡아내는지도
일부러 망가뜨려서 확인했습니다 (구분자 깨뜨리기 / 값에 공백 넣기 / 잘림 표시 지우기 →
셋 다 걸렸습니다).

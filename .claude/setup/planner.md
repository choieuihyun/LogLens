# planner: 합격 기준을 받아 새 방을 어디에 지을지 도면만 그리는 설계사

## 무엇을 하나

합격 기준을 보고 어떤 파일을 새로 만들지, 어느 폴더에 둘지, 어떤 기존 코드를 본보기로 삼을지 정한다.
화면이 있으면 합격 기준에 나온 대상 이름마다 자동화가 찾을 식별자를 어디에 붙일지도 정한다.
구현을 작은 단계로 쪼개고 위험을 적는다. 코드는 쓰지 않는다.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/feature` | 2단계 설계 |
| `/feature` | 3단계 계획 검증이 실패하면 지적 사항을 들고 다시 불린다 (3회 초과면 사람 판단) |
| `/feature` | 4단계 승인에서 사용자가 수정을 요청해 설계로 돌아올 때 |

## 못 하는 것

- 기존 파일을 고치지 못한다 (Edit 없음). Write 는 `plan.json` 저장에만 쓰고, 이것은 문서 규칙으로 막혀 있다
- 의존성 추가나 빌드 설정 변경을 계획에 넣지 않는다. 사용자가 따로 허락해야 한다
- 프로젝트에 없는 구조나 추상화 층을 새로 들이지 않는다. 주변 코드를 따른다
- 고칠 기존 파일은 후보만 적는다. 확정은 explorer 몫이다

## 넘겨주는 것

`plan.json`: 새로 만들 파일, 고칠 후보, 본보기, 식별자 매핑, 주 도메인, 단계, 위험.
오케스트레이터가 새 파일 목록을 수정 허가 목록에 넣고, plan-checker 가 기준을 다 채우는지 검증하며,
explorer 가 고칠 후보를 확정한다. 주 도메인은 시나리오 태그가 되어 런타임 게이트가 무엇을 재생할지 정한다.

## 여기에 넣으면 좋아지는 것

- 화면이 없는 프로젝트(서버, 라이브러리, CLI)라고 알려 주면 식별자 매핑을 건너뛰고 설계에 집중한다
- 도메인 폴더 규칙을 알려 주면 새 파일을 알맞은 곳에 두어 바뀐 도메인의 시나리오만 재생된다.
  모바일이면 기능별 패키지, 웹이면 `src/features/<이름>`, 서버면 모듈별 디렉토리
- 본보기로 삼을 화면이나 엔드포인트를 알려 주면 매번 비슷한 곳을 찾느라 헤매지 않는다
- 규칙이 모르는 새 폴더를 만들어도 되는지 알려 주면 전체 회귀로 떨어지는 배치를 피한다

## 질문

| # | 사용자에게 할 질문 | 스캔으로 추측 | 저장 위치 | 안 채우면 |
|---|---|---|---|---|
| 1 | 사용자가 보는 화면이 있나요? | UI 프레임워크 의존성, 화면이나 컴포넌트 폴더 유무 | `project.has_ui` | 모름(null)은 화면이 있는 것으로 본다. 식별자 매핑을 계속 요구하고 식별자 속성이 비면 위험으로 적는다 |
| 2 | 폴더 이름이 곧 도메인인 곳이 있나요? 그 상위 경로, 공유 폴더, 도메인 목록을 알려 주세요 | 소스 트리에서 기능별로 나뉜 하위 폴더 | `domains.dir_rules` | 모든 변경이 ALL(전체 회귀)이 된다. 상위 경로가 빈 항목도 규칙으로 치지 않는다 |
| 3 | 한 폴더에 섞여 있고 파일 이름 앞부분으로 도메인이 갈리는 곳이 있나요? | 같은 폴더 파일 이름의 공통 접두사 | `domains.prefix_rules` | 위와 같다 |
| 4 | 새 기능이 기존 도메인 폴더에 안 맞으면 새 폴더를 만들어도 되나요? 어디에 두나요? | 불가 | `.claude/project/agents/planner.md` | 가능하면 규칙이 아는 폴더에 두고, 아니면 주 도메인을 적어 시나리오 태그로만 맞춘다 |
| 5 | 새 화면이나 엔드포인트를 만들 때 본보기로 삼을 기존 코드가 있나요? | 최근에 만들어진 같은 종류 파일 | `.claude/project/agents/planner.md` | 컨벤션 문서가 없으면 비슷한 기존 코드 한 곳을 스스로 골라 근거로 삼는다 |

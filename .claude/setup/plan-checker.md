# plan-checker: 공사 시작 전에 설계도를 요구사항표와 한 줄씩 맞대 보는 감리

## 무엇을 하나

새 기능을 만들기 전에, 세운 계획(plan.json)이 약속한 완료 조건(spec.json)을 전부 채우는지 거꾸로 따져 본다.
빠진 조건, 화면 자동화가 요소를 찾을 이름표 누락, 손대면 안 되는 파일을 건드리려는 계획을 찾아낸다.
문제를 찾아 보고만 하고 계획은 고치지 않는다. 고치는 일은 planner 가 다시 한다.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/feature` | 3단계 계획 검증 (PLAN-CHECK). FAIL 이면 planner 로 돌아가고, 세 번 넘게 반복되면 사람에게 넘긴다 |

## 못 하는 것

- 소스 수정 도구 없음(Edit 없음): 판정하는 쪽이 고치면 판정이 자기 편이 된다. 고치는 일은 planner 재호출로 한다
- Write 는 `plan-check.json` 저장 전용, 전체 코드 스캔과 git 금지: 지시로 막음, 도구로는 안 막힘 (Write, Bash, Grep 이 있다). 계획만 보는 게이트라 탐색은 explorer 몫이다

## 넘겨주는 것

`<session_dir>/plan-check.json` 에 판정(PASS / PASS_WITH_NOTES / FAIL)과 문제 목록, 수용조건 커버리지를 남긴다.
오케스트레이터가 읽어 FAIL 이면 문제 목록을 planner 에게 넘겨 다시 계획하게 하고,
PASS_WITH_NOTES 면 MEDIUM 항목을 4단계 승인 요약에 넣어 사용자에게 보여 준다.

## 여기에 넣으면 좋아지는 것

- 손대면 안 되는 파일 패턴: 모바일은 서명 설정과 자동 생성 코드, 웹은 빌드 산출물과 잠금 파일, 서버는 이미 배포된 DB 마이그레이션 파일. 이것을 알면 계획 단계에서 FORBIDDEN_PLAN 으로 막는다
- 화면 유무와 UI 식별자 속성: 웹의 `data-testid`, 모바일의 `testTag` 처럼 무엇으로 요소를 찾는지 알면 이름표 누락을 정확히 잡는다. 서버나 라이브러리는 이 검사가 "해당 없음" 이 된다
- 새 화면이나 새 엔드포인트가 갖춰야 할 구조: 컨벤션 문서에 적혀 있으면 STRUCTURE_GAP 을 근거 있게 판정한다
- 보고에서 강조할 항목: 예를 들어 외부 결제 서버 흐름 누락(SERVER_GAP)을 승인 요약 맨 앞에 두게 할 수 있다. 판정 기준과 심각도는 바뀌지 않는다

## 질문

| # | 사용자에게 할 질문 | 스캔으로 추측 | 저장 위치 | 안 채우면 |
|---|---|---|---|---|
| 1 | 사람이 손으로 만들지 않은 코드가 있나요? (자동 생성 코드, 외부에서 복사해 온 벤더 코드, 빌드 산출물) | generated 폴더, vendor 폴더, `.gitignore` 의 산출물 경로 | `forbidden_globs` | 금지 없음. 계획이 그 파일을 고치려 해도 FORBIDDEN_PLAN 이 나오지 않는다 |
| 2 | 사람만 손대야 하는 파일이 있나요? (서명 키, 배포 설정, CI 설정, 이미 적용된 DB 마이그레이션) | keystore, `.env`, CI 설정 폴더, migrations 폴더 | `forbidden_globs` | 위와 같다 |
| 3 | 계획 검증 보고에서 특히 앞세워 보여 줬으면 하는 항목이 있나요? (판정 기준은 바뀌지 않고 보고 순서와 강조만 바뀝니다) | 불가 | `.claude/project/agents/plan-checker.md` | 뼈대 보고 형식대로 HIGH 항목만 요약한다 |

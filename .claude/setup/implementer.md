# implementer: 허가받은 구역 안에서만 공사하는 시공 담당

## 무엇을 하나

탐색 단계가 정하고 오케스트레이터가 허가한 파일 목록 안에서만 실제로 코드를 고친다.
버그 수정과 신규 기능 구현을 맡는다. 목록 밖을 고쳐야 하면 고치지 않고 실패로 알린다.
프로젝트의 컨벤션 문서가 있으면 먼저 읽고 그 규칙대로 쓰며, 없으면 주변 코드를 따른다.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/fix` | 2단계 수정 (IMPLEMENTING). 빌드 실패나 게이트 재생 실패(triage 가 REAL_BUG 로 판정) 뒤 다시 불린다. 시도 상한에 닿으면 멈춘다 |
| `/feature` | 6단계 구현. 검증 또는 빌드가 실패하면 다시 불린다. 신규 sync 흐름은 feature-mode 지시로 허용된다 |


## 못 하는 것

- 명령 실행 (Bash 없음): 빌드, 테스트, git 을 못 돌린다. 빌드는 builder 가 따로 해야 "고쳤다" 는 말을 따로 확인할 수 있다
- 검색 (Grep, Glob 없음): 어디를 고칠지는 explorer 가 이미 정했다. 스스로 범위를 넓히지 못하게 한다
- 허가 목록 밖 파일, 빌드 설정 파일 수정 (규칙): 범위를 넘는 수정은 검증이 안 된 수정이다
- 전체 리팩토링, 없는 아키텍처 패턴 도입, 언어 전환, API 변경 (규칙): 최소 수정 원칙

## 넘겨주는 것

코드는 파일에 직접 반영하고, 최근 패치 기록(바꾼 줄 수, 대상 파일, 변경 해시)을 남긴다.
오케스트레이터가 이 기록으로 "아무것도 안 바꿨다" 거나 "같은 자리를 맴돈다" 를 잡아 멈춘다.
바뀐 코드는 builder 가 컴파일하고, `/feature` 에서는 verifier 가 완료 기준을 검사한다.

## 여기에 넣으면 좋아지는 것

- 컨벤션 문서를 가리키면 위험 축마다 이 프로젝트의 구체 규칙을 따른다. 예: 모바일은 화면이 닫히면 진행 중 작업 취소, 웹은 전역 store 갱신 방식, 서버는 요청 처리 스레드에서 막는 호출 금지
- UI 자동화 식별자 속성을 알려 주면 고치는 화면의 버튼, 입력, 목록에 식별자를 붙여 E2E 가 요소를 찾게 한다
- 쓰는 아키텍처 패턴을 문서에 적어 두면 "없는 패턴 도입 금지" 가 정확해진다
- 먼저 따를 참고 파일이나 손대지 말아야 할 관례를 알려 주면 주변 코드 짐작이 준다

## 질문

| # | 사용자에게 할 질문 | 스캔으로 추측 | 저장 위치 | 안 채우면 |
|---|---|---|---|---|
| 1 | 코딩 컨벤션 문서가 있는가. 있다면 경로는 (아키텍처 패턴, 주석과 이름 규칙, 위험 축별 규칙, 완료 기준을 담는 곳) | CONTRIBUTING, docs 폴더의 스타일 문서, 린트 설정 | `docs.conventions` | 컨벤션 검증을 건너뛴다. 위험 축의 기본 규칙과 주변 코드만 따른다 |
| 2 | UI 자동화가 요소를 찾을 때 쓰는 식별자 속성 이름은 (화면이 없으면 해당 없음. 화면 유무는 planner 설명서에서 묻는다) | 기존 코드의 testTag, testID, data-testid 사용 빈도 | `ui_test_id` | 식별자를 붙이지 않는다. 셀렉터 규칙 검증도 건너뛰고 E2E 가 요소를 못 찾을 수 있다 |
| 3 | 수정할 때 우선 참고할 파일이나, 규칙은 아니지만 피해 온 관례가 있는가 | 불가 | `.claude/project/agents/implementer.md` | 주변 코드만 보고 판단한다 |
| 4 | 도메인마다 절대 깨면 안 되는 불변식이나 흔한 함정이 있는가 | 불가 | `DOMAIN.md` | 불변식을 모른 채 고친다. `docs.domain_map` 이 비어 있으면 읽지 않는다 |

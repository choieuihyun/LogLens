# verifier: 설계도대로 지어졌는지 둘러보고 적기만 하는 준공 검사관

## 무엇을 하나

새 기능 코드가 "다 됐다" 고 할 수 있는 상태인지 검사한다. 빌드는 컴파일만 보니, 컴파일로는 안 잡히는 것을 본다.
이 프로젝트가 정한 완료 기준을 지켰는지, 테스트가 누를 버튼에 식별자가 붙었는지, 새로 만든 화면이나 엔드포인트가
실제로 어딘가에 연결됐는지를 본다. 문제를 찾아 적을 뿐 고치지 않는다.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/feature` | 7단계 검증 + 빌드. builder 와 나란히 |
| `/fix` | 불리지 않는다. 빌드와 런타임 게이트만 본다 |

## 못 하는 것

- 파일을 고치거나 쓰지 못한다 (Edit, Write 없음). 검사관이 고치기 시작하면 무엇을 검사했는지 흐려진다
- 결과도 파일로 쓰지 않고 반환만 한다. 오케스트레이터가 `verifier.json` 으로 저장한다
- Bash 는 완료 기준 검사 스크립트에만 쓴다. 빌드와 git 은 문서 규칙으로 막혀 있다

## 넘겨주는 것

`verifier.json`: 통과 여부, 문제 목록(종류, 심각도, 파일, 줄), 해당 없던 항목.
오케스트레이터가 builder 결과와 합쳐 판단한다. 심각도 MEDIUM 이상이 하나라도 있으면 실패이고,
문제 목록이 implementer 에게 그대로 넘어가 수정 근거가 된다. LOW 는 보고에만 남는다.

## 여기에 넣으면 좋아지는 것

- 기계로 확정되는 완료 기준. 모바일이면 "화면 파일에 미리보기 선언 필수", 웹이면 "컴포넌트에 색상 값 직접 쓰기 금지",
  서버면 "핸들러 파일에 입력 검증 호출 필수" 같은 규칙을 적어 두면 눈대중 대신 매번 같은 결과가 나온다
- 새 코드를 등록해야 하는 파일 (웹 라우트 설정, 앱 매니페스트나 내비게이션 그래프, 서버 라우터, 의존성 주입 설정) 을
  알려 주면 "만들었지만 아무도 안 부르는 코드" 를 덜 놓친다
- 컨벤션 문서가 없으면 "잘 된 예" 파일 하나가 코드 판단의 기준이 된다

| 1 | 완료 기준 중 기계로 확인되는 것이 있나요? "이 패턴의 파일에는 이 문자열이 꼭 있어야 한다 / 있으면 안 된다" 형태로 알려 주세요 | 같은 종류 파일(화면, 컴포넌트, 핸들러)에 공통으로 나오는 선언이나 금지 패턴 | `dod_checks` | 검사 스크립트가 exit 2 를 내고 "기계 검증을 못 했다" 로 보고한다. 통과로 세지 않고 코드 판단만 한다 |
| 2 | 새 화면, 엔드포인트, 모듈을 만들면 등록해야 하는 파일은 어디인가요? (라우트 설정, 내비게이션, 서버 라우터, 의존성 주입 설정) | 라우터, 매니페스트, 주입 설정 파일 이름 | `.claude/project/agents/verifier.md` | 일반 목록으로 Grep 해서 부르는 곳을 찾는다. 등록 방식이 특이하면 연결 누락을 놓친다 |
| 3 | 컨벤션 문서가 없을 때 코드 판단의 기준으로 삼을 "잘 된 예" 파일이 있나요? | 최근 수정이 많고 구조가 가지런한 파일 | `.claude/project/agents/verifier.md` | 구조, 하드코딩, 수용조건 경로의 일반 항목만 본다 |

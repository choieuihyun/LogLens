# discuss: 만들기 전에 "이런 경우는요?" 를 먼저 묻는 기획 회의 진행자

## 무엇을 하나

새 기능을 만들기 전에 사용자와 대화해 범위를 정한다.
모호한 것만 묻지 않고 예외 상황, 파생되는 엣지 케이스, 같이 있으면 좋을 기능을 먼저 꺼낸다.
최대 5라운드까지 묻고, 정한 것과 뺀 것과 못 정한 것을 나눠 기록한다. 어떻게 만들지는 정하지 않는다.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/feature` | 0단계 기획 토론. 결과가 없거나 범위가 비면 다시 불린다 |
| `/feature` | 4단계 승인에서 사용자가 수정을 요청해 기획 토론으로 돌아올 때 |

## 못 하는 것

- 기존 파일을 고치지 못한다 (Edit 없음). 기획 단계에서 코드가 바뀌면 뒤 단계의 기준이 흔들린다
- Write 는 있지만 `discuss.json` 저장에만 쓴다. 이것은 도구가 아니라 문서 규칙으로 막혀 있다
- 구현 방법을 설계하지 않는다. 그건 planner 몫이고, 여기서는 무엇을, 왜, 어디까지만 정한다
- 저장소 전체를 훑지 않는다. 질문 근거가 될 코드만 최소로 본다

## 넘겨주는 것

`discuss.json`: 합의 범위, 제외 범위, 예외 처리, 위험 표시(동기화, 외부 시스템, 상태 전파, 스레드, DB, 새 진입점, 권한), 미해결 논점.
오케스트레이터가 위험 표시로 위험 수준을 올리고, spec 이 합의 범위를 합격 기준으로 바꾸고,
planner 가 외부 시스템과 동기화 표시를 설계에 반영한다.

## 여기에 넣으면 좋아지는 것

- 외부 시스템 이름을 알려 주면 "어느 서버가 관여하나요" 대신 이름을 들어 묻는다.
  모바일이면 푸시 서버, 웹이면 결제 대행 API, 서버면 다른 팀의 메시지 큐
- 상태의 원본이 서버인지 로컬인지, 여러 기기에 동시에 떠 있는지 알려 주면 충돌 정책을 먼저 묻는다
- 이 프로젝트에 해당 없는 축(오프라인 모드 없음, 권한 개념 없음)을 알려 주면 헛질문이 줄어든다
- 자주 거절되는 제안 종류를 알려 주면 범위를 부풀리는 제안을 덜 한다

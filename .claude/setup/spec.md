# spec: 만들기 전에 합격 기준을 먼저 적어 봉인하는 시험 출제자

## 무엇을 하나

기획 토론에서 합의한 범위를 "이 상태에서 이렇게 하면 이렇게 보여야 한다" 는 합격 기준으로 바꾼다.
만든 뒤에 결과를 보고 테스트를 쓰면 만든 대로 통과하는 빈 테스트가 되므로, 반드시 만들기 전에 적는다.
각 기준은 자동 재생 시나리오로 옮길 수 있게 시작점, 조작 대상, 확인 대상을 이름으로 적는다.

## 언제 불리나

| 커맨드 | 단계 |
|---|---|
| `/feature` | 1단계 명세 동결. 기준이 비거나 미해결 질문이 남으면 다시 불린다 (3회 초과면 사람 판단) |
| `/feature` | 7.5단계 시나리오 생성 때 진입 스텝이 비어 있으면 다시 불린다 |

## 못 하는 것

- 기존 파일을 고치지 못한다 (Edit 없음). Write 는 `spec.json` 저장에만 쓰고, 이것은 문서 규칙으로 막혀 있다
- 사용자에게 직접 묻지 못한다 (AskUserQuestion 없음). 모르는 것은 미해결 질문으로 남기고 오케스트레이터가 묻는다
- 토론에서 정하지 않은 범위를 더하지 않는다. 구현 방법도 정하지 않는다 (planner 몫)

## 넘겨주는 것

`spec.json`: 합격 기준 목록. 기준마다 자동 재생으로 볼 수 있는지, 사람이 봐야 하는지, 진입 스텝, 조작과 확인 대상 이름, 확인할 텍스트.
planner 가 대상 이름을 UI 식별자로 옮기고, 오케스트레이터가 7.5단계에서 이것만 보고 시나리오를 만들며,
verifier 가 그 식별자가 코드에 붙었는지 확인한다.

## 여기에 넣으면 좋아지는 것

- 자동화가 로그인을 통과하는 방법을 알려 주면 사람 검증으로 빠지는 기준이 줄어든다.
  모바일이면 테스트 빌드 전용 로그인 진입, 웹이면 저장해 둔 세션 상태 파일, 서버면 테스트 토큰 발급 경로
- 시나리오의 시작점과 환경별 값의 자리표시자 이름을 알려 주면 진입 스텝이 한 번에 확정된다
- 테스트 데이터를 만드는 방법(시드 스크립트, 픽스처, 테스트용 API)을 알려 주면 준비 스텝이 구체적이 된다
- 여러 기기나 세션을 동시에 재생할 수 있는지 알려 주면 동기화 기준을 자동으로 볼지 사람이 볼지 정확히 가른다

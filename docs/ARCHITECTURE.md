# 아키텍처 — 동작 원리

[기획서](../기획서.md)가 *무엇을 왜 만드는가*라면, 이 문서는 *실제로 어떻게 도는가*다.
call site 에서 브라우저 픽셀까지 한 줄이 어떤 경로로 흐르는지, 각 경계에서 무엇이
보장되는지, 왜 그렇게 잘랐는지를 적는다.

- 계약의 문법 정의는 [RECORD_FORMAT.md](RECORD_FORMAT.md)
- 초안에서 바뀐 결정과 그 이유는 [DECISIONS.md](DECISIONS.md)

---

## 0. 한눈에

```
┌─ 안드로이드 기기 ─────────────────────┐
│                                       │
│  앱 코드                              │
│   LogLens.i(AUTH,"LOGIN_OK","uid",7)  │
│        │                              │
│        ▼                              │
│  ┌──────────────────────────────┐     │
│  │ (A) 로깅 라이브러리          │     │
│  │  게이팅→포맷→정화→마스킹     │     │
│  │  →절단→싱크 팬아웃           │     │
│  └───────┬──────────────┬───────┘     │
│          ▼              ▼             │
│    android.util.Log   파일            │
│          │          (날짜별)          │
│          ▼              │             │
│    [logcat 링버퍼]      │             │
└──────────┬──────────────┼─────────────┘
           │ USB / TCP    │
           │ (adb)        │
═══════════╪══════════════╪═════════════  ← 기기 경계
           ▼              ▼
┌─ 개발 PC ─────────────────────────────┐
│  ┌──────────────────────────────┐     │
│  │ (B) 뷰어 — 로컬 파이썬 프로세스     │
│  │                              │     │
│  │  Source(adb│file│synth)      │     │
│  │        │ 원문 한 줄           │     │
│  │        ▼                     │     │
│  │  Parser  접두사→본문          │     │
│  │        │ Record              │     │
│  │        ▼                     │     │
│  │  Hub  링버퍼 + 이슈트레이     │     │
│  │        │ 팬아웃              │     │
│  │        ▼                     │     │
│  │  HTTP 서버 (stdlib)          │     │
│  └────────┬─────────────────────┘     │
│           │ SSE (text/event-stream)   │
│           ▼                           │
│      브라우저 GUI                      │
│      탭 / 필터 / 이슈 / 대시보드        │
└───────────────────────────────────────┘
```

경계는 셋이다.

| 경계 | 넘어가는 것 | 보장 |
|---|---|---|
| 앱 → logcat | 정화·마스킹·절단이 끝난 **한 줄** | 개행 없음, 4KB 이내, PII 마스킹 완료 |
| 기기 → PC | `adb logcat -v threadtime` 의 텍스트 스트림 | 포맷 고정, 끊기면 자동 재연결 |
| 서버 → 브라우저 | 파싱된 `Record` 의 JSON 배치 | 100ms 배치, 느린 구독자는 드롭 |

**두 컴포넌트 사이에 코드 의존이 없다.** 공유하는 건 가운데의 한 줄 텍스트 규격뿐이다.
라이브러리를 자바로 쓰든 코틀린으로 다시 쓰든, 뷰어를 파이썬에서 Go 로 옮기든
반대쪽은 알 필요가 없다.

## 1. (A) emitter — call site 에서 logcat 까지

### 1.1 파이프라인

```
LogLens.i(AppDomain.AUTH, "LOGIN_OK", "uid", 7, "token", jwt, "msg", "로그인 성공")
   │
   ├─① 레벨 게이팅        Level.enabled(isDebug)     ← 여기서 끊기면 문자열 조립조차 안 함
   ├─② 싱크 스냅샷        synchronized 블록에서 복사  ← 이후 팬아웃은 락 밖에서
   │
   ├─③ Formatter.body()
   │     ├─ evt= 이벤트          Sanitizer.event()
   │     ├─ varargs 쌍 순회
   │     │    ├─ 키 검증          [A-Za-z_][A-Za-z0-9_]*  아니면 쌍을 버리고 경고
   │     │    ├─ "msg" 키         → 자유 메시지로 분리
   │     │    ├─ 값 정화          Sanitizer.value()   공백→_, |→/, 개행→\n
   │     │    └─ 마스킹           Masker.apply()      정확 키 매칭
   │     ├─ Throwable            → err=Class:msg  at=Frame:line
   │     ├─ 메시지 정화           Sanitizer.message() 개행만 잡고 공백은 살림
   │     └─ 절단                 Truncator.truncate() 코드포인트 경계 + ...[cut]
   │
   └─④ 싱크 팬아웃        각 Sink.write(level, tag, body), 예외는 삼킴
           ├─ LogcatSink → android.util.Log.i(tag, body)
           └─ FileSink   → "2026-08-12 11:23:45.678 I/APP_AUTH: <body>"
```

### 1.2 왜 이 순서인가

**게이팅이 맨 앞인 이유.** 릴리스 빌드에서 `LogLens.d(...)` 는 varargs 배열 하나만
만들고 즉시 반환한다. 문자열 연결도, 정화도, 마스킹도 일어나지 않는다. 로깅 표준이
성능 때문에 거부당하는 걸 막는 가장 값싼 방법이다.

> 함정 하나: 라이브러리 모듈의 `BuildConfig.DEBUG` 는 **그 라이브러리의** 빌드타입이라
> 앱이 release 여도 true 일 수 있다. 그래서 `LogLens.init(isDebug)` 로 앱이 주입하거나
> `LogLensAndroid.install()` 이 `ApplicationInfo.FLAG_DEBUGGABLE` 을 런타임에 읽는다.
> 초기화 전 기본값은 **디버그 아님** — 잊었을 때 V/D 가 새는 것보다 빠지는 게 안전하다.

**마스킹이 정화 뒤인 이유.** 마스킹 결과(`***`)도 공백 없는 토큰이어야 계약이 유지된다.
정화 → 마스킹 순서면 마스킹은 그냥 치환이고, 반대면 마스킹 산출물을 다시 검사해야 한다.

**절단이 맨 마지막인 이유.** 필드를 다 붙인 뒤의 최종 길이라야 의미가 있다.
그리고 절단은 **바이트로 세고 코드포인트로 자른다** — 한글 3바이트, 이모지 4바이트
(서로게이트 페어)라 순진하게 바이트로 자르면 문자가 반으로 갈린다.

### 1.3 모듈 경계

| 모듈 | 아는 것 | 모르는 것 |
|---|---|---|
| `lib/core` | 문자열 규격, 정화, 마스킹, 절단, 싱크 인터페이스 | **안드로이드, 도메인 목록, 서드파티** |
| `lib/android` | `android.util.Log`, `ApplicationInfo` | 도메인 목록 |
| 앱 | 자기 도메인 목록 | 규격의 세부 |

`core` 가 안드로이드를 모르는 게 설계의 지렛대다. 덕분에

- 일반 JVM 에서 `javac` 만으로 컴파일·테스트된다 (JUnit 조차 없이)
- **뷰어 파서와의 왕복 검증**을 실제로 돌릴 수 있다 (§6)
- 자바 서버·데스크톱 앱에도 그대로 붙는다

### 1.4 도메인 주입

```java
// 라이브러리 — 도메인을 모른다
public interface LogDomain { String tag(); }

// 앱 — 자기 도메인을 정의한다
public enum AppDomain implements LogDomain {
    AUTH, CHAT, NET, FILE_XFER;
    public String tag() { return "APP_" + name(); }
}
```

도메인 목록은 프로젝트의 정체성이다. 라이브러리에 enum 으로 박는 순간 재사용이 끝난다.
인터페이스 하나로 뒤집으면 라이브러리는 도메인 불가지가 되고, 각 프로젝트가 자기 것을 꽂는다.

## 2. 계약 — 두 컴포넌트가 공유하는 유일한 것

```
<접두사> <PREFIX>_<DOMAIN>: evt=<EVENT> k=v k=v | <자유 메시지>
└────────┘ └────────────┘  └──────────────────────────────────┘
 소스마다 다름    태그              본문 = 진짜 계약
```

### 2.1 태그가 곧 도메인인 이유

`Log.d("APP", "[AUTH] 로그인 성공")` 처럼 태그를 본문에 넣는 래퍼가 흔하다.
그 순간 logcat 의 태그 필터가 무력화된다 — 모든 로그의 태그가 `APP` 하나니까.

도메인을 태그 자리에 그대로 두면 **도메인 필터가 공짜로 따라온다**:

```bash
adb logcat -s APP_AUTH:*        # 우리 뷰어 없이도 도메인 필터가 된다
```

Android Studio Logcat 에서도, 순수 adb 에서도 동작한다. 이게 vendor lock-in 없는 표준의 조건이다.

### 2.2 한 줄 = 한 레코드

logcat 은 한 줄이 4KB 근처를 넘으면 **자기가 자른다**. 어디서 자를지는 우리가 모른다.
그래서 우리가 먼저 자르고 `...[cut]` 을 붙인다.

여러 줄로 쪼개는 선택지는 기각했다. 쪼개면 파서가 2번째 줄부터를 이해하지 못하고,
멀티스레드 환경에서 다른 스레드의 로그가 사이에 끼면 복구 자체가 불가능하다.

### 2.3 접두사는 계약이 아니다

초안은 접두사와 본문을 하나의 정규식으로 잡으려 했고, 그게 틀렸다.
`adb logcat` 의 표준 포맷들은 **연도를 찍지 않는데** 초안 정규식은 `\d{4}-\d\d-\d\d` 를
요구했다. 사실 연도가 있는 건 우리가 소유한 파일 싱크 포맷이었다.

```
threadtime :  08-12 11:23:45.678  4321  4390 E APP_NET: <본문>
brief      :  E/APP_NET( 4321): <본문>
파일 싱크  :  2026-08-12 11:23:45.678 E/APP_NET: <본문>
              └──────── 접두사 ────────┘        └본문┘
```

→ **얇은 접두사 파서 3종 + 공용 본문 파서 1개.** 접두사는 소스마다 다르고, 계약은 본문뿐이다.

## 3. 뷰어가 기기에 "붙는" 원리

여기가 이 프로젝트에서 설명할 가치가 가장 큰 부분이다.

### 3.1 문제: 브라우저는 USB 를 못 본다

웹 GUI 를 원하는데 브라우저 샌드박스는 USB·adb 소켓·임의 프로세스 실행을 막는다.
(WebUSB 는 안드로이드 ADB 인터페이스에 접근할 수 없고, 애초에 adb 서버가 기기를
독점하고 있다.)

선택지는 셋이었다:

| 방법 | 문제 |
|---|---|
| Electron 앱 | 200MB 런타임, 배포 무거움, 브라우저를 이미 잘 쓰는데 |
| 로그를 파일로 뽑아 업로드 | 실시간이 아님. "지금 이 버튼 눌렀을 때"를 못 봄 |
| **로컬 브리지 프로세스** | ← 채택 |

### 3.2 해법: 로컬 프로세스가 통역한다

```
    브라우저                로컬 파이썬 프로세스              기기
       │                          │                          │
       │  GET /                   │                          │
       │─────────────────────────>│                          │
       │  <html>                  │                          │
       │<─────────────────────────│                          │
       │                          │                          │
       │  GET /api/config         │   adb shell pidof <pkg>  │
       │─────────────────────────>│─────────────────────────>│
       │  {prefix,tabs,source}    │   551                    │
       │<─────────────────────────│<─────────────────────────│
       │                          │                          │
       │  GET /api/stream         │  adb logcat -v threadtime│
       │─────────────────────────>│─────────────────────────>│
       │  200 text/event-stream   │                          │
       │<─────────────────────────│   ...로그 스트림...       │
       │                          │<─────────────────────────│
       │  event: logs             │                          │
       │  data: [{...},{...}]     │  (파싱 → 링버퍼 → 팬아웃) │
       │<─────────────────────────│                          │
       │  event: logs             │                          │
       │<─────────────────────────│                          │
       │        (계속)            │        (계속)             │
```

브라우저는 **HTTP 만 한다.** USB 는 로컬 프로세스가 본다. 둘 사이는 SSE 한 방향 스트림.

### 3.3 adb 를 무는 구체적 방법

```python
subprocess.Popen(
    ["adb", "-s", serial, "logcat", "-v", "threadtime"],
    stdout=PIPE, text=True, encoding="utf-8", errors="replace", bufsize=1)
```

네 가지를 의도적으로 고정했다:

**① 포맷을 명시적으로 못 박는다 (`-v threadtime`).**
adb 기본 포맷은 버전·환경에 따라 다르다. 기본값에 맡기면 어느 날 남의 PC 에서
파서가 조용히 깨진다. 파서가 아는 포맷을 호출 시점에 강제한다.
(`AdbSource.describe()["format"]` 이 이 값을 노출하고, 테스트가 파서 쪽과 일치를 검사한다.)

**② `errors="replace"`.** 기기가 깨진 바이트를 뱉어도 스트림이 죽으면 안 된다.
한 줄이 손상되는 건 감수하고, 파이프라인은 계속 돈다.

**③ `bufsize=1` (줄 버퍼링).** 안 그러면 4KB 블록이 찰 때까지 로그가 안 나온다.
"버튼 누르면 바로 뜬다"가 이 도구의 존재 이유라 지연을 허용할 수 없다.

**④ pid 자동추적.** `adb shell pidof <package>` 로 대상 앱 pid 를 푼다.
앱이 재시작되면 pid 가 바뀌므로 **연결할 때마다 다시 푼다**.
뷰어 UI 는 이 pid 를 "이 앱만" 토글로 노출한다. 시스템 태그 수백 종을 한 번에 걷어내는
가장 강력한 필터다.

> 단, **이슈를 클릭한 상태에서는 pid 필터를 양보한다.** ANR 은 앱이 아니라
> `ActivityManager`(system_server pid)가 찍기 때문에, pid 로 거르면 방금 클릭한
> 이슈가 화면에서 사라진다.

### 3.4 재연결 — 예외가 아니라 정상 동작

기기 sleep, USB 재연결, 앱 재시작, `adb kill-server`. 스트림은 **끊긴다**.
이걸 상위 레이어가 알게 하면 모든 레이어가 재연결을 알아야 한다.

`AdbSource.lines()` 는 무한 제너레이터다. 안에서:

```
while not stopped:
    기기 없으면 → 마커 emit → 2초 대기 → 재시도
    pid 재확인
    logcat 프로세스 기동 → 줄 yield
    프로세스 종료 → 마커 emit → 재시도
```

소비자(`Reader` 스레드)는 그냥 `for line in source.lines()` 이고, 끊김을 모른다.
상태 변화는 `--------- loglens: <메시지>` 마커 줄로 흘려보낸다. 이 줄은
파서가 RAW 로 처리하고, Hub 가 가로채 UI 상태 표시줄로 올린다. **별도 채널이 필요 없다.**

### 3.5 소스 추상화 — adb 만이 아니다

```
LogSource (인터페이스)
  ├── AdbSource       실기기. 재연결·pid추적·포맷고정
  ├── FileSource      저장된 로그 재생 / tail -f
  └── SyntheticSource 합성 생성기 — 기기 없이 데모·개발·테스트
```

이 이음매가 주는 것:

- **기기 없이 뷰어 전체를 개발·테스트·데모**할 수 있다 (이 저장소의 테스트 전부가 그렇다)
- 로드맵의 `.session` 저장/공유가 붙을 자리가 이미 있다
- CI 에서 adb 없이 통합 테스트가 돈다

## 4. 뷰어 내부

### 4.1 프로세스·스레드 모델

```
파이썬 프로세스 (단일)
│
├── Reader 스레드 (1개)
│     for line in source.lines():
│         rec = parser.parse(line)      ← 순수 함수, 예외 없음
│         hub.ingest(rec)
│
├── Hub  (공유 상태, threading.Lock)
│     ├── deque(maxlen=20000)   링버퍼
│     ├── IssueTray             규칙별·그룹키별 카운터
│     └── [Queue, Queue, ...]   구독자별 큐 (탭 하나당 하나)
│
└── ThreadingHTTPServer
      └── 요청마다 스레드
            ├── GET /api/stream  → 장수명. 큐를 빨아 SSE 로 밀어냄
            └── 그 외            → 단명. JSON/정적파일
```

파서가 **단일 스레드**인 게 중요하다. 로그는 초당 수천 줄이 올 수 있지만 정규식
매칭은 싸고, 순서 보존이 중요하다. 병렬화하면 순서가 깨지고 얻는 게 없다.

### 4.2 링버퍼 + 팬아웃 + 백프레셔

`Hub.ingest()` 한 번에 일어나는 일:

```python
with lock:
    seq += 1
    buffer.append(rec)          # 링버퍼 — maxlen 이 알아서 오래된 걸 버림
    tray.observe(rec)           # 이슈 규칙 매칭 + 카운트
    for q in subscribers:
        try: q.put_nowait(payload)
        except Full:
            q.get_nowait()      # ← 가장 오래된 걸 버리고 새 걸 넣는다
            q.put_nowait(payload)
```

**백프레셔 정책이 "느린 구독자를 굶긴다"** 인 게 의도적이다.
백그라운드 탭이나 멈춘 브라우저 때문에 전체 파이프라인이 막히면 안 된다.
로그 뷰어에서 오래된 줄을 잃는 건 감수할 만한 손실이고, 실시간성이 막히는 건 아니다.

### 4.3 SSE 프로토콜

```
event: logs
data: [{"kind":"structured","level":"I","domain":"AUTH",...}, {...}]

: ping
```

- **100ms 배치.** 줄마다 이벤트를 보내면 초당 수천 개 DOM 이벤트가 발생해 브라우저가
  죽는다. 100ms 동안 모아 배열 하나로 보낸다. 사람 눈에 100ms 는 즉시다.
- **15초 하트비트** (`: ping` 주석 프레임). 유휴 연결을 프록시나 브라우저가 끊는 걸 막는다.
- **구독은 헤더보다 먼저.** 순서가 반대면 클라이언트가 헤더를 받은 시점과 구독 성립
  시점 사이의 레코드를 조용히 놓친다. (API 테스트를 쓰다가 이 경합에 걸려 발견했다)
- **재연결은 브라우저가 한다.** `EventSource` 는 끊기면 스스로 재접속한다.
  우리는 상태 표시만 바꾼다.

### 4.4 파싱 파이프라인

```
원문 한 줄
   │
   ├─ 접두사 매칭 (3종 순차 시도)         ── 실패 → RAW (원문 보존, 회색 표시)
   │     ts, pid, tid, level, tag, body
   │
   ├─ body.rstrip()                       ── 줄 끝 공백 관용
   │
   ├─ 태그 매칭  ^<PREFIX>_([A-Z0-9_]+)$  ── 실패 → UNSTRUCTURED (레거시/시스템)
   │     domain
   │
   └─ 본문 매칭  evt=... k=v ... | msg    ── 실패 → UNSTRUCTURED (규격 위반/잘림)
         event, fields, msg               ── 성공 → STRUCTURED
```

**세 가지 강등 등급이 있고, 아무것도 버리지 않는다.**

| kind | 언제 | 화면 |
|---|---|---|
| `structured` | 우리 태그 + 규격 준수 | 도메인 칩 + 이벤트 + 필드 칩 + 메시지 |
| `unstructured` | 레거시 태그, 또는 우리 태그인데 규격 위반 | 태그 + 본문 |
| `raw` | 접두사조차 못 읽음 (구분선, 손상된 줄) | 원문 회색 |

이게 **점진 도입의 기술적 기반**이다. 라이브러리를 안 쓰는 앱에 붙여도 뷰어는
그냥 동작하고(색칠된 logcat), call site 를 하나 옮길 때마다 그 줄만 리치해진다.
"전부 이관해야 쓸 수 있다"는 요구가 없다.

> **다만 "장벽이 없다"와 "call site #1 부터 값이 나온다"는 다른 말이다.**
> 강등 사다리는 *들어오는 문턱*을 없애 줄 뿐, 분석 기능을 켜 주지는 않는다.
> 가치 곡선의 무릎은 **한 흐름 전체를 계측했을 때** 온다 — §11 참고.

**파서는 절대 예외를 던지지 않는다.** 잘린 줄, 제어문자, 5000자짜리 쓰레기가 다 들어온다.
파싱 실패는 예외가 아니라 강등이다.

### 4.5 집계 — 구조화 로그라서 가능한 것

`GET /api/stats` 는 링버퍼 전체(기본 2만 줄)를 훑어 그 자리에서 집계한다.

```
레코드 → (domain, event, fields) 튜플
   ├── 도메인/이벤트 빈도        Counter
   ├── 성공률                    이벤트 접미사 _OK/_FAIL 로 판정
   ├── 실패 사유 분포            reason/err/code 필드에서 추출
   └── 퍼널 이탈                 flowId 로 흐름 묶기, 없으면 카운트 근사
```

범용 logcat 뷰어가 원리상 못 하는 게 이거다. 문자열밖에 없으면 group-by 할 키가 없다.
우리는 emitter 단에서 이미 키-값으로 쪼개 놨으니 그냥 세면 된다.

> 퍼널은 `flowId` 유무에 따라 모드가 갈리고, **어느 모드인지 UI 에 표시한다.**
> 근사값을 정확한 값인 척하지 않는다.

### 4.6 브라우저 쪽

```
EventSource ──> state.records[]  (클라이언트 링버퍼 20000)
                     │
                     ├── 필터 체인 passes(r)
                     │     레벨 → 구조화만 → 도메인 탭 → 이슈 필터 → pid → 검색
                     │
                     └── 최근 1500줄만 DOM 렌더 (100ms 스로틀)
```

- **필터는 전부 클라이언트.** 서버 왕복 없이 즉각 반응한다. 2만 줄 순회는 1ms 수준.
- **렌더 상한 1500줄.** 그 이상은 사람이 못 읽고 DOM 만 무거워진다.
  가상 스크롤 대신 상한 + 검색으로 푼다 — 코드가 1/10 이다.
- **자동스크롤 자동 해제.** 사용자가 위로 스크롤하면 끈다. 읽는 중에 끌려가지 않게.

## 6. 검증 구조

```
        Java Formatter ──생성──> 한 줄 ──> Python Parser ──> 필드 대조
             (emitter)                        (viewer)
```

이 저장소에서 가장 중요한 검사다. 이유는 이렇다.

손으로 쓴 픽스처는 **양쪽에 같은 오해를 심을 수 있다.** 내가 파서를 잘못 이해한 채로
픽스처를 쓰면 픽스처 테스트는 통과한다. 두 구현이 서로를 검사해야 그 오해가 드러난다.

기대값은 Formatter 의 출력을 되읽어 만들지 않는다 — 입력으로부터 독립적으로 조립한다.
그리고 이 검사가 실제로 파손을 잡는지 **음성 대조**로 확인했다
(구분자 파손 / 필드에 공백 주입 / 잘림 표식 제거 → 셋 다 검출).

| 검사 | 범위 | 방법 |
|---|---|---|
| `make test-viewer` | 파서·집계·설정·서버 API | Python `unittest`, 픽스처 + 실제 HTTP 호출 |
| `make test-lib` | 정화·마스킹·절단·포맷·게이팅·싱크 | 자체 하네스 (한글·이모지를 여러 절단 한도에서) |
| `make roundtrip` | **계약 그 자체** | Java 생성 → Python 파싱 → 대조 |
| `make demo` | end-to-end | 진짜 emitter → 파일 → 뷰어 |

## 7. 성능 특성과 한계

| 항목 | 수치 / 성질 |
|---|---|
| 서버 링버퍼 | 기본 20,000줄 (`bufferSize`). 넘으면 오래된 것부터 폐기 |
| 대시보드 집계 범위 | 링버퍼 전체. 그 이전 이력은 없다 |
| SSE 배치 | 100ms |
| 구독자 큐 | 2,000건. 넘치면 가장 오래된 것부터 드롭 |
| 클라이언트 버퍼 / 렌더 | 20,000줄 보관 / 최근 1,500줄 렌더 |
| 파싱 비용 | 줄당 정규식 최대 4회. 단일 스레드로 초당 수만 줄 수준 |

**한계 (알고 있고, 감수한 것)**

- **영속성 없음.** 뷰어를 끄면 버퍼가 사라진다. 장기 보관은 라이브러리의 파일 싱크 담당이고,
  세션 저장(`.session`)은 로드맵이다.
- **집계는 버퍼 범위.** "어제 대비 성공률" 같은 건 못 한다. 서버 수집 파이프라인의 영역이다.
- **flowId 없으면 퍼널은 근사.** 상관 ID 는 처음부터 넣어야 한다 (기획서 §9-5).
- **단일 기기.** 여러 기기 동시 관찰은 프로세스를 여러 개 띄우는 것으로 푼다.
- **난독화 스택 복원(retrace) 없음.** 로드맵.

## 9. 처음 붙일 때 (0 → 1)

이관을 시작하지 않은 프로젝트에 붙이는 실제 순서다.

**① 지형부터 본다 — config 자동 생성**

```bash
loglens --source adb --package com.your.app --init your-app.json
```

기기의 현재 logcat 최근 N줄을 표본으로 읽어, **대상 앱 pid 가 찍은 태그만** 골라
이름으로 군집화하고 탭 초안을 만든다. (`ChatListFragment` 와 `Chats` 는 한 탭으로 합친다.)
**태그 이름과 빈도만 읽는다 — 메시지 본문은 집계에도 출력에도 쓰지 않는다.**

이미 이관된 도메인이 있으면 그건 그대로 도메인 탭이 되고, 아직인 것은
`legacyTagPattern` 탭이 된다.

**② 붙여서 본다**

```bash
loglens --source adb --package com.your.app --config your-app.json
```

아직 구조화 0%다. 지금은 "탭이 달린 logcat"이고, 이게 정상이다.
**뷰어의 가치는 emission 이 규격을 지킬 때 생긴다** — 기획서 §1 의 그 지점.

**③ 한 흐름을 통째로 옮긴다** (call site 하나가 아니라)

```java
// before
Log.d("ChatListFragment", "send fail, room=" + room + " " + e.getMessage());

// after
LogLens.e(AppDomain.CHAT, "SEND_FAIL", e, "room", room);
```

옮긴 줄부터 도메인 칩·필드 칩·이슈 트레이에 들어간다. 하지만 **성공률 차트가
뜨려면 성공·실패가 쌍으로** 있어야 하고, 퍼널은 흐름 전체에 `flowId` 가 필요하다.
그래서 한 줄씩 흩어서 옮기지 말고 **흐름 하나를 골라 끝까지** 옮기는 게 낫다 —
거기서 처음으로 범용 도구가 못 하는 화면이 나온다(§11).

**옛 로그는 반드시 지운다** — 추가만 하면 잡음과 구조가 공존해 오히려 두 배가 된다
(기획서 §9-1).

**④ 탭의 `domains` 를 채운다**

`legacyTagPattern` 은 그대로 두고 `domains` 에 새 도메인을 넣으면,
이관된 줄과 아직인 줄이 **같은 탭에서 나란히** 보인다. 이관 진행도가 눈에 보인다.

**⑤ 규격이 자리 잡으면 퍼널을 정의한다**

`flowId` 를 심고 `config.json` 의 `funnels` 에 단계를 나열하면
단계별 이탈률이 대시보드에 뜬다.

## 11. 이 도구가 요구하는 것 — 그리고 그게 왜 리스크인가

앞의 열 절은 *어떻게 도는가*였다. 이 절은 **언제 값을 못 내는가**다.
설계의 가장 큰 리스크라서 마지막에 따로 둔다.

### 기능별 요구 조건

| 기능 | 필요 조건 | 통합 0줄로? |
|---|---|:--:|
| 레벨 · 검색 · 정규식 필터 | 없음 | ✅ |
| pid 필터, 도메인 탭 라우팅 | 없음 | ✅ |
| 크래시 · ANR · 네이티브 이슈 그룹핑 | 없음 — 시스템 로그를 파싱 | ✅ |
| 도메인 / 이벤트 빈도 | 구조화 레코드 | ❌ |
| 성공률 | 이벤트 이름을 `_OK` / `_FAIL` 로 통일 | ❌ |
| 실패 사유 분포 | 실패 레코드에 `reason=` / `err=` | ❌ |
| 퍼널 이탈 | 흐름 전체에 `flowId=` + 단계 정의 | ❌ |

**✅ 세 줄만으로는 Android Studio Logcat 을 이길 수 없다.**
차별점은 전부 ❌ 쪽에 있고, 전부 규칙에 의존한다.

### 가치 곡선의 무릎

기획서 §11 은 "call site #1 부터 가치"라고 적었다. **실제 동작보다 낙관적이다.**

```
 값
  │                                    ┌────  퍼널·이탈률
  │                          ┌─────────┘
  │                ┌─────────┘               성공률·실패사유
  │      ┌─────────┘
  │──────┘                                   칩·검색·이슈그룹핑
  └──────┬─────────┬──────────┬─────────────────────────
       통합 0     call site   흐름 하나        도메인 전체
                    1개        전부
                             ↑ 무릎
```

call site 하나를 옮기면 색칠된 칩 하나를 얻는다. 성공률은 성공·실패 이벤트가
**쌍으로** 있어야 뜨고, 퍼널은 흐름 **전체**에 `flowId` 가 박혀야 뜬다.
**실질적 최소 단위는 call site 하나가 아니라 "한 흐름 전체"다.**

이관을 계획한다면 "여기저기 한 줄씩"이 아니라 **"흐름 하나를 골라 끝까지"** 가 맞다.

### 그래서 이건 무엇인가

지저분한 로그를 고쳐 주는 도구가 아니다.
**규율을 지키면 그게 보상으로 돌아오게 만드는 도구다.**

규칙을 어긴 로그는 사라지지 않는다 — 그냥 분석에서 빠진다(§06 강등 사다리).
벌이 아니라 **비대칭**이고, 그 비대칭이 채택 유인이다.
같은 성질이 OpenTelemetry · Sentry · 구조화 로깅 전반에 있다. 넣은 만큼 나온다.

### 의존을 줄이는 두 갈래 (미구현)

**① 파서 쪽 필드 추출.** 메커니즘은 이미 있다 — 크래시 이슈 그룹핑은 통합 0줄인데도
`config.json` 의 정규식으로 원문에서 예외 클래스명을 뽑아낸다. 이 추출을 이슈 트레이
말고 **레코드 자체**에 적용하면(레거시 태그 + 패턴 → 도메인/이벤트/필드) 앱을 한 줄도
안 고치고 대시보드가 켜진다.

취약하다. 개발자가 로그 문자열을 바꾸면 규칙이 조용히 깨지고, 그건 이 프로젝트가
벗어나려던 바로 그 취약함이다. **다리이지 목적지가 아니다** — "값을 먼저 보여주고
이관을 설득한다"는 순서를 만드는 용도다.

**② codemod.** `Log.d(TAG, "...")` 를 기계적으로 변환하는 도구.
이관 비용이 사람 손이 아니라 스크립트가 되면 채택 논쟁 자체가 사라진다. 근본책이다.

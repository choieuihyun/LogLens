# 동작 원리

[기획서](../기획서.md)가 *무엇을 왜 만드는가*라면, 이 문서는 *실제로 어떻게 도는가*입니다.
앱에서 로그를 찍는 순간부터 브라우저 화면에 뜨기까지 한 줄이 어떤 경로로 흐르는지,
각 단계에서 무엇이 보장되는지, 왜 그렇게 나눴는지를 적었습니다.

- 로그 형식의 문법 정의는 [RECORD_FORMAT.md](RECORD_FORMAT.md)
- 초안에서 바뀐 결정과 그 이유는 [DECISIONS.md](DECISIONS.md)

용어 몇 개를 먼저 정리해 둡니다.

| 이 문서에서 | 뜻 |
|---|---|
| **형식** | 라이브러리와 뷰어가 지키기로 한 로그 한 줄의 모양. 둘을 잇는 유일한 접점입니다 |
| **레코드** | 형식에 맞게 찍힌 로그 한 줄, 또는 그걸 파싱한 결과 |
| **출력 대상(Sink)** | 로그를 실제로 내보내는 곳. logcat, 파일 등 |
| **링버퍼** | 크기가 정해진 저장소. 꽉 차면 오래된 것부터 밀려납니다 |

## 0. 전체 그림

```
┌─ 안드로이드 기기 ─────────────────────┐
│                                       │
│  앱 코드                              │
│   LogLens.i(AUTH,"LOGIN_OK","uid",7)  │
│        │                              │
│        ▼                              │
│  ┌──────────────────────────────┐     │
│  │ (A) 로깅 라이브러리          │     │
│  │  레벨 확인 → 문자열 조립     │     │
│  │  → 값 정리 → 마스킹          │     │
│  │  → 길이 자르기 → 출력        │     │
│  └───────┬──────────────┬───────┘     │
│          ▼              ▼             │
│    android.util.Log   파일            │
│          │          (날짜별)          │
│          ▼              │             │
│    [logcat 링버퍼]      │             │
└──────────┬──────────────┼─────────────┘
           │ USB / TCP    │
           │ (adb)        │
═══════════╪══════════════╪═════════════  ← 기기와 PC의 경계
           ▼              ▼
┌─ 개발 PC ─────────────────────────────┐
│  ┌──────────────────────────────┐     │
│  │ (B) 뷰어 — 파이썬 프로그램        │     │
│  │                              │     │
│  │  읽는 곳(adb│file│synth)      │     │
│  │        │ 원문 한 줄           │     │
│  │        ▼                     │     │
│  │  파서                        │     │
│  │        │ 레코드              │     │
│  │        ▼                     │     │
│  │  Hub  링버퍼 + 이슈 목록      │     │
│  │        │                    │     │
│  │        ▼                     │     │
│  │  HTTP 서버                   │     │
│  └────────┬─────────────────────┘     │
│           │ SSE (실시간 전송)          │
│           ▼                           │
│      브라우저 화면                     │
│      탭 / 필터 / 이슈 / 분석           │
└───────────────────────────────────────┘
```

넘어가야 하는 경계가 세 군데 있고, 각각에서 보장하는 게 다릅니다.

| 경계 | 넘어가는 것 | 보장하는 것 |
|---|---|---|
| 앱 → logcat | 값 정리·마스킹·길이 자르기가 끝난 한 줄 | 줄바꿈 없음, 4KB 이내, 민감 정보 가려짐 |
| 기기 → PC | `adb logcat -v threadtime`이 출력하는 텍스트 | 형식 고정, 끊기면 자동 재연결 |
| 서버 → 브라우저 | 파싱된 레코드를 JSON으로 묶은 것 | 100ms씩 묶어서 전송, 못 따라오는 쪽은 오래된 것부터 버림 |

**두 컴포넌트는 서로의 코드를 참조하지 않습니다.** 공유하는 건 가운데의 로그 한 줄
형식뿐입니다. 라이브러리를 코틀린으로 다시 쓰든 뷰어를 Go로 옮기든 반대쪽은
알 필요가 없습니다.

## 1. 로깅 라이브러리 — 호출부에서 logcat까지

### 1.1 처리 순서

```
LogLens.i(AppDomain.AUTH, "LOGIN_OK", "uid", 7, "token", jwt, "msg", "로그인 성공")
   │
   ├─① 레벨 확인          릴리스면 V/D는 여기서 끝. 문자열도 안 만듭니다
   ├─② 출력 대상 복사     synchronized 안에서 목록만 복사. 실제 전달은 락 밖에서
   │
   ├─③ 문자열 조립
   │     ├─ evt= 이벤트           이름 정리
   │     ├─ 키-값 쌍 순회
   │     │    ├─ 키 검증           [A-Za-z_][A-Za-z0-9_]*  아니면 그 쌍은 버리고 경고
   │     │    ├─ "msg" 키          자유 메시지로 따로 빼둠
   │     │    ├─ 값 정리           공백→_, |→/, 줄바꿈→\n 문자 두 개로
   │     │    └─ 마스킹            민감한 키면 값을 *** 로
   │     ├─ 예외가 있으면          err=클래스:메시지  at=발생위치
   │     ├─ 메시지 정리            줄바꿈만 처리하고 공백은 그대로
   │     └─ 길이 자르기            글자 단위로 자르고 ...[cut] 붙이기
   │
   └─④ 출력 대상에 전달   각각 write() 호출. 예외가 나면 삼킵니다
           ├─ LogcatSink → android.util.Log.i(tag, body)
           └─ FileSink   → "2026-08-12 11:23:45.678 I/APP_AUTH: <본문>"
```

### 1.2 왜 이 순서인가

**레벨 확인이 맨 앞인 이유.** 릴리스 빌드에서 `LogLens.d(...)`를 부르면 인자 배열
하나만 만들고 바로 돌아옵니다. 문자열을 이어 붙이지도, 값을 정리하지도, 마스킹하지도
않습니다. 로깅 표준이 "느려진다"는 이유로 거부당하는 걸 막는 가장 싼 방법입니다.

> 여기 함정이 하나 있습니다. 라이브러리 모듈의 `BuildConfig.DEBUG`는 **그 라이브러리의**
> 빌드 타입이라, 앱을 release로 빌드해도 true로 남을 수 있습니다. 그러면 릴리스 앱에서
> V/D 로그가 전부 새어 나갑니다. 그래서 앱이 `LogLens.init(isDebug)`로 직접 알려주거나,
> `LogLensAndroid.install()`이 앱의 `FLAG_DEBUGGABLE`을 실행 중에 읽습니다.
> 초기화 전 기본값은 "디버그 아님"입니다. 깜빡했을 때 로그가 새는 것보다 안 찍히는 게
> 안전하니까요.

**마스킹이 값 정리 뒤인 이유.** 마스킹 결과인 `***`도 공백 없는 한 덩어리여야 형식이
유지됩니다. 정리 → 마스킹 순서면 마스킹은 그냥 문자열 치환이면 되는데, 반대로 하면
마스킹 결과를 다시 검사해야 합니다.

**길이 자르기가 맨 마지막인 이유.** 필드를 다 붙인 뒤의 최종 길이라야 의미가 있습니다.
그리고 자를 때는 **바이트 수로 세되 글자 단위로 끊습니다**. 한글은 UTF-8에서 3바이트,
이모지는 4바이트라서, 바이트 위치로 그냥 자르면 글자가 반으로 갈려 깨집니다.

### 1.3 모듈이 아는 것과 모르는 것

| 모듈 | 아는 것 | 모르는 것 |
|---|---|---|
| `lib/core` | 문자열 형식, 값 정리, 마스킹, 길이 자르기, 출력 인터페이스 | **안드로이드, 도메인 목록, 외부 라이브러리** |
| `lib/android` | `android.util.Log`, `ApplicationInfo` | 도메인 목록 |
| 앱 | 자기 도메인 목록 | 형식의 세부 사항 |

`core`가 안드로이드를 모르는 게 이 설계에서 가장 이득이 큰 부분입니다.

- 일반 JVM에서 `javac`만으로 컴파일하고 테스트할 수 있습니다 (테스트 프레임워크도 없이)
- **뷰어 파서와 서로 대조하는 검증**을 실제로 돌릴 수 있습니다 (§8)
- 자바 서버나 데스크톱 앱에도 그대로 붙습니다

### 1.4 도메인은 앱이 정합니다

```java
// 라이브러리 — 도메인이 뭔지 모릅니다
public interface LogDomain { String tag(); }

// 앱 — 자기 도메인을 정의합니다
public enum AppDomain implements LogDomain {
    AUTH, CHAT, NET, FILE_XFER;
    public String tag() { return "APP_" + name(); }
}
```

도메인 목록은 프로젝트마다 다릅니다. 라이브러리에 enum으로 넣어 버리면 다른 프로젝트에서
못 씁니다. 인터페이스 하나로 뒤집으면 라이브러리는 도메인을 몰라도 되고,
각 프로젝트가 자기 것을 꽂아 넣습니다.

## 2. 로그 한 줄의 형식

```
<접두사> <PREFIX>_<DOMAIN>: evt=<이벤트> 키=값 키=값 | <자유 메시지>
└───────┘ └────────────┘  └──────────────────────────────────┘
소스마다 다름     태그              본문 — 여기가 진짜 약속
```

### 2.1 태그 자리에 도메인을 넣는 이유

`Log.d("APP", "[AUTH] 로그인 성공")`처럼 태그를 본문에 적는 방식이 흔합니다.
그런데 그러면 모든 로그의 태그가 `APP` 하나가 되어서 logcat의 태그 필터가 무의미해집니다.

도메인을 태그 자리에 그대로 두면 **도메인 필터가 공짜로 따라옵니다**:

```bash
adb logcat -s APP_AUTH:*        # 우리 뷰어 없이도 도메인별로 걸러집니다
```

Android Studio Logcat에서도, 순수 adb에서도 됩니다. 특정 도구에 묶이지 않는 표준이
되려면 이 조건이 필요합니다.

### 2.2 한 줄에 레코드 하나

logcat은 한 줄이 4KB 근처를 넘으면 **자기가 잘라 버립니다.** 어디서 자를지는 우리가
알 수 없습니다. 그래서 우리가 먼저 자르고 `...[cut]`을 붙입니다.

여러 줄로 쪼개는 방법도 있지만 안 썼습니다. 쪼개면 파서가 두 번째 줄부터를 이해하지
못하고, 멀티스레드 환경에서 다른 스레드의 로그가 사이에 끼면 복구할 방법이 없습니다.

### 2.3 줄 앞부분은 약속에 포함되지 않습니다

초안은 줄 앞부분(타임스탬프 등)과 본문을 정규식 하나로 잡으려 했는데, 그게 틀렸습니다.
`adb logcat`의 표준 출력 형식들은 **연도를 안 찍는데** 초안 정규식은 `\d{4}-\d\d-\d\d`를
요구했습니다. 연도가 있는 건 사실 우리가 만든 파일 저장 형식이었습니다.

```
threadtime :  08-12 11:23:45.678  4321  4390 E APP_NET: <본문>
brief      :  E/APP_NET( 4321): <본문>
파일 저장  :  2026-08-12 11:23:45.678 E/APP_NET: <본문>
              └────── 줄 앞부분 ──────┘        └본문┘
```

그래서 **줄 앞부분을 읽는 작은 파서 3개 + 본문을 읽는 파서 1개**로 나눴습니다.
앞부분은 어디서 읽었느냐에 따라 다르고, 약속인 것은 본문뿐입니다.

## 3. 뷰어가 기기에 붙는 방법

이 프로젝트에서 설명할 값어치가 가장 큰 부분입니다.

### 3.1 문제: 브라우저는 USB를 못 봅니다

웹 화면으로 보고 싶은데, 브라우저 보안 정책이 USB·adb 소켓·프로그램 실행을 전부 막습니다.
WebUSB라는 게 있긴 하지만 안드로이드 ADB 인터페이스에는 접근할 수 없고, 애초에
adb 서버가 이미 기기를 독점하고 있습니다.

선택지가 셋이었습니다.

| 방법 | 문제 |
|---|---|
| Electron 앱으로 만들기 | 200MB짜리 런타임을 같이 배포해야 함. 브라우저를 이미 잘 쓰고 있는데 |
| 로그를 파일로 뽑아서 올리기 | 실시간이 아님. "지금 이 버튼 눌렀을 때"를 못 봄 |
| **PC에서 도는 작은 프로그램을 중간에 두기** | ← 이걸로 했습니다 |

### 3.2 해결: 중간 프로그램이 통역합니다

```
    브라우저                PC의 파이썬 프로그램              기기
       │                          │                          │
       │  GET /                   │                          │
       │─────────────────────────>│                          │
       │  <html>                  │                          │
       │<─────────────────────────│                          │
       │                          │                          │
       │  GET /api/config         │   adb shell pidof <pkg>  │
       │─────────────────────────>│─────────────────────────>│
       │  {prefix,tabs,source}    │   551                    │
       │<─────────────────────────│<─────────────────────────│
       │                          │                          │
       │  GET /api/stream         │  adb logcat -v threadtime│
       │─────────────────────────>│─────────────────────────>│
       │  200 text/event-stream   │                          │
       │<─────────────────────────│   ...로그 스트림...       │
       │                          │<─────────────────────────│
       │  event: logs             │                          │
       │  data: [{...},{...}]     │  (파싱 → 링버퍼 → 전달)   │
       │<─────────────────────────│                          │
       │        (계속)            │        (계속)             │
```

브라우저는 **HTTP만 합니다.** USB는 PC 프로그램이 봅니다.
둘 사이는 SSE(서버가 브라우저로 밀어주는 단방향 스트림)로 연결합니다.

### 3.3 adb를 실행하는 구체적인 방법

```python
subprocess.Popen(
    ["adb", "-s", serial, "logcat", "-v", "threadtime"],
    stdout=PIPE, text=True, encoding="utf-8", errors="replace", bufsize=1)
```

네 가지를 일부러 고정했습니다.

**① 출력 형식을 명시합니다 (`-v threadtime`).**
adb의 기본 형식은 버전이나 환경에 따라 다릅니다. 기본값에 맡기면 어느 날 다른 사람 PC에서
파서가 조용히 깨집니다. 파서가 아는 형식을 실행할 때 강제로 지정합니다.
(`AdbSource.describe()["format"]`이 이 값을 알려주고, 테스트가 파서 쪽과 일치하는지 확인합니다.)

**② `errors="replace"`.** 기기가 깨진 바이트를 내보내도 스트림이 죽으면 안 됩니다.
한 줄이 망가지는 건 감수하고 나머지는 계속 읽습니다.

**③ `bufsize=1` (줄 단위 버퍼링).** 이게 없으면 4KB가 찰 때까지 로그가 안 나옵니다.
"버튼 누르면 바로 뜬다"가 이 도구를 만든 이유라서 지연을 허용할 수 없습니다.

**④ 앱 프로세스 ID를 매번 다시 찾습니다.** `adb shell pidof <package>`로 대상 앱의
프로세스 ID를 알아냅니다. 앱을 재시작하면 ID가 바뀌기 때문에 연결할 때마다 다시 찾습니다.

> **앱 ID 필터가 결정적입니다.** 실제 사내 앱에 붙여 봤더니, 대상 앱 ID로 거르는 것만으로
> 시스템·다른 앱 태그 140여 종이 한 번에 사라지고 그 앱이 찍은 태그 여덟 개만 남았습니다.
> 이 필터가 없으면 화면이 쓸모가 없습니다.
>
> 다만 **이슈를 클릭해서 보는 중에는 이 필터를 끕니다.** ANR은 앱이 아니라
> `ActivityManager`(시스템 프로세스)가 찍기 때문에, 앱 ID로 거르면 방금 클릭한 이슈가
> 화면에서 사라집니다.

### 3.4 재연결은 예외 상황이 아니라 평소 동작입니다

기기가 잠들거나, USB를 다시 꽂거나, 앱을 재시작하거나, `adb kill-server`를 하면
스트림이 끊깁니다. 이걸 위쪽 코드가 알게 하면 *모든* 계층이 재연결을 처리해야 합니다.

그래서 로그를 읽는 쪽(`AdbSource.lines()`)을 끝나지 않는 반복문으로 만들었습니다.

```
반복:
    기기가 없으면 → 상태 메시지 내보내고 → 2초 기다렸다가 → 다시 시도
    앱 프로세스 ID 다시 확인
    logcat 프로세스 실행 → 읽은 줄을 하나씩 내보냄
    프로세스가 끝나면 → 상태 메시지 내보내고 → 다시 시도
```

이걸 쓰는 쪽은 그냥 `for line in source.lines()`이고 끊김을 모릅니다.
상태 변화는 `--------- loglens: <메시지>` 같은 특별한 줄로 흘려보냅니다.
파서는 이 줄을 "형식에 안 맞는 줄"로 처리하고, Hub가 가로채서 화면 상태 표시줄에
올립니다. **별도 통로를 만들 필요가 없습니다.**

### 3.5 로그를 어디서 읽을지 고를 수 있습니다

```
LogSource (인터페이스)
  ├── AdbSource       실제 기기. 재연결·앱 추적·형식 고정
  ├── FileSource      저장해 둔 로그 재생 / tail -f
  └── SyntheticSource 가짜 로그 생성 — 기기 없이 데모·개발·테스트
```

이렇게 나눠 두면:

- **기기 없이 뷰어 전체를 개발하고 테스트하고 시연**할 수 있습니다
  (이 저장소의 테스트가 전부 그렇습니다)
- 나중에 세션 저장/재생 기능을 붙일 자리가 이미 있습니다
- CI에서 adb 없이 통합 테스트가 돕니다

## 4. 뷰어 내부

### 4.1 스레드 구성

```
파이썬 프로세스 (하나)
│
├── 읽기 스레드 (1개)
│     for line in source.lines():
│         rec = parser.parse(line)      ← 예외를 안 던지는 순수 함수
│         hub.ingest(rec)
│
├── Hub  (공유 상태, Lock으로 보호)
│     ├── deque(maxlen=20000)   링버퍼
│     ├── IssueTray             규칙별·묶음별 카운터
│     └── [Queue, Queue, ...]   브라우저 탭마다 큐 하나
│
└── HTTP 서버 (요청마다 스레드)
      ├── GET /api/stream  → 오래 살아있음. 큐에서 꺼내 SSE로 밀어냄
      └── 나머지            → 금방 끝남. JSON이나 정적 파일
```

파싱을 **스레드 하나에서만** 하는 게 중요합니다. 로그는 초당 수천 줄이 올 수 있지만
정규식 매칭 자체는 싸고, 순서가 유지되는 게 더 중요합니다. 병렬로 돌리면 순서가 깨지는데
얻는 건 없습니다.

### 4.2 받는 쪽이 못 따라올 때

`Hub.ingest()` 한 번에 일어나는 일입니다.

```python
with lock:
    seq += 1
    buffer.append(rec)          # 링버퍼 — 꽉 차면 알아서 오래된 게 밀려남
    tray.observe(rec)           # 이슈 규칙 검사 + 카운트
    for q in subscribers:
        try: q.put_nowait(payload)
        except Full:
            q.get_nowait()      # ← 가장 오래된 걸 버리고 새 걸 넣습니다
            q.put_nowait(payload)
```

**못 따라오는 브라우저 탭은 오래된 로그를 잃습니다.** 이게 의도한 동작입니다.
백그라운드에 있거나 멈춘 탭 하나 때문에 전체가 막히면 안 되니까요. 로그 뷰어에서
오래된 줄 몇 개를 잃는 건 감수할 만하지만, 실시간이 막히는 건 그렇지 않습니다.

### 4.3 브라우저로 밀어주는 방식 (SSE)

```
event: logs
data: [{"kind":"structured","level":"I","domain":"AUTH",...}, {...}]

: ping
```

- **100ms씩 묶어서 보냅니다.** 줄마다 이벤트를 보내면 초당 수천 개 이벤트가 발생해서
  브라우저가 버티지 못합니다. 100ms 동안 모아서 배열 하나로 보냅니다.
  사람 눈에 100ms는 즉시로 느껴집니다.
- **15초마다 신호를 보냅니다** (`: ping`). 아무것도 안 오가면 중간의 프록시나 브라우저가
  연결을 끊어 버리는 걸 막습니다.
- **구독 등록을 응답 헤더보다 먼저 합니다.** 순서가 반대면, 브라우저가 헤더를 받은
  시점과 서버에 구독이 등록된 시점 사이에 들어온 로그를 조용히 놓칩니다.
  (API 테스트를 작성하다가 이 문제를 발견했습니다.)
- **재연결은 브라우저가 알아서 합니다.** `EventSource`가 끊기면 스스로 다시 붙습니다.
  서버는 상태 표시만 바꿉니다.

### 4.4 파싱 단계

```
원문 한 줄
   │
   ├─ 줄 앞부분 읽기 (3가지 형식 순서대로 시도)  ── 실패 → RAW (원문 그대로 회색 표시)
   │     시각, 프로세스ID, 스레드ID, 레벨, 태그, 본문
   │
   ├─ 본문 끝의 공백 제거                         ── 공백 하나 때문에 버리지 않도록
   │
   ├─ 태그 확인  ^<PREFIX>_([A-Z0-9_]+)$          ── 실패 → UNSTRUCTURED (예전 로그, 시스템 로그)
   │     도메인
   │
   └─ 본문 확인  evt=... 키=값 ... | 메시지        ── 실패 → UNSTRUCTURED (형식 위반, 잘림)
         이벤트, 필드, 메시지                      ── 성공 → STRUCTURED
```

**등급이 셋 있고, 어느 경우에도 줄을 버리지 않습니다.**

| 등급 | 언제 | 화면에서 |
|---|---|---|
| `structured` | 우리 태그 + 형식을 지킴 | 도메인 칩 + 이벤트 + 필드 칩 + 메시지 |
| `unstructured` | 예전 태그이거나, 우리 태그인데 형식 위반 | 태그 + 본문 |
| `raw` | 줄 앞부분조차 못 읽음 (구분선, 망가진 줄) | 원문 회색 |

덕분에 **라이브러리를 안 쓰는 앱에 붙여도 뷰어가 그냥 동작합니다.** 색만 입힌 logcat이긴
하지만요. 그리고 호출부를 하나씩 옮길 때마다 그 줄만 자세해집니다.
"전부 다 바꿔야 쓸 수 있다"는 요구가 없습니다.

> 다만 **"시작하는 문턱이 없다"와 "호출부 하나만 바꿔도 값이 나온다"는 다른 이야기입니다.**
> 이 3단계 구조는 문턱을 없애 줄 뿐, 분석 기능을 켜 주지는 않습니다. §11을 보세요.

**파서는 어떤 입력에도 예외를 던지지 않습니다.** 잘린 줄, 제어문자, 5000자짜리 쓰레기가
다 들어옵니다. 파싱 실패는 예외가 아니라 등급을 낮추는 것으로 처리합니다.

### 4.5 집계 — 형식을 지켜야 가능한 것

`GET /api/stats`를 부르면 링버퍼 전체(기본 2만 줄)를 훑어서 그 자리에서 계산합니다.

```
레코드 → (도메인, 이벤트, 필드) 로 쪼개져 있음
   ├── 도메인/이벤트 빈도        그냥 세기
   ├── 성공률                    이벤트 이름 끝이 _OK 인지 _FAIL 인지로 판정
   ├── 실패 사유 분포            reason / err / code 필드에서 꺼냄
   └── 단계별 이탈               flowId 로 같은 흐름끼리 묶기, 없으면 개수로 근사
```

일반 logcat 뷰어가 이걸 못 하는 이유는 간단합니다. 문자열밖에 없으면 무엇을 기준으로
묶을지가 없습니다. 우리는 로그를 찍을 때 이미 키-값으로 쪼개 놨으니 그냥 세면 됩니다.

> 단계별 이탈은 `flowId`가 있느냐에 따라 계산 방식이 달라지는데, **어느 방식인지 화면에
> 표시합니다.** 근사값을 정확한 값처럼 보여주지 않기 위해서입니다.

### 4.6 브라우저 쪽

```
EventSource ──> state.records[]  (브라우저에도 링버퍼 2만 줄)
                     │
                     ├── 필터 순서
                     │     레벨 → 형식에 맞는 것만 → 도메인 탭 → 이슈 → 앱 ID → 검색어
                     │
                     └── 최근 1500줄만 화면에 그림 (100ms마다)
```

- **필터는 전부 브라우저에서 합니다.** 서버에 다시 물어보지 않으니 즉시 반응합니다.
  2만 줄을 순회해도 1ms 수준입니다.
- **화면에는 1500줄까지만 그립니다.** 그 이상은 사람이 못 읽고 화면만 무거워집니다.
  가상 스크롤 대신 개수 제한 + 검색으로 해결했습니다. 코드가 10분의 1입니다.
- **위로 스크롤하면 자동 스크롤이 꺼집니다.** 읽는 중에 화면이 끌려가지 않도록요.

## 5. 기술 선택

| 부분 | 선택 | 이유 |
|---|---|---|
| 라이브러리 core | **순수 자바 8** | 안드로이드나 외부 라이브러리를 안 쓰니 JVM에서 테스트할 수 있고, 뷰어와 대조 검증이 가능합니다. minSdk 21, 자바 앱에도 그대로 씁니다. 코틀린으로 편하게 쓰는 층은 나중에 위에 얹으면 됩니다 |
| 라이브러리 android | 자바 + `android.util.Log` | 안드로이드에 닿는 유일한 모듈이라 얇게 유지합니다 |
| 라이브러리 테스트 | **직접 만든 테스트 코드** | "외부 라이브러리 0개"를 테스트에서도 지킵니다. `javac`와 `java`만으로 242개 검사가 돕니다 |
| 뷰어 | **Python 3.8+ 표준 라이브러리만** | `pip install` 없이 파일 복사만으로도 돕니다. 단일 실행 파일로 묶기도 쉽고, 사내망 제약이 있는 환경에서도 됩니다 |
| 뷰어 서버 | `http.server.ThreadingHTTPServer` | SSE에 필요한 건 오래 유지되는 연결과 스레드뿐입니다. Flask나 FastAPI를 쓸 이유가 없습니다 |
| 실시간 전송 | **SSE** | 한 방향이면 충분합니다. WebSocket보다 단순하고, 재연결이 브라우저에 내장돼 있습니다 |
| 웹 화면 | **바닐라 JS + CSS** | 빌드 단계가 없습니다. 서버가 정적 파일 3개를 그대로 내보냅니다. 프레임워크를 넣는 순간 `npm install`이 배포 조건이 됩니다 |
| 기기 연결 | `adb` 프로세스 실행 | 공식 도구입니다. USB, TCP, 에뮬레이터를 adb가 전부 추상화해 줍니다 |
| 설정 | JSON + JSON Schema | 스키마가 있으면 에디터에서 자동완성이 되고, 잘못된 키를 파일 읽는 시점에 잡을 수 있습니다 |
| 빌드 | `make` (라이브러리 배포용으로 gradle) | 검증 전체가 `make test` 한 줄입니다 |

### 일부러 안 쓴 것

| 안 쓴 것 | 이유 |
|---|---|
| Electron | 웹 화면 하나 때문에 200MB 런타임을 배포할 이유가 없습니다. 로컬 서버로 같은 걸 얻습니다 |
| WebSocket | 양방향이 필요 없습니다. 브라우저에서 서버로는 평범한 HTTP로 충분합니다 |
| React / Vue | 빌드 파이프라인이 배포 조건이 됩니다. 화면 하나짜리 도구에는 과합니다 |
| DB (SQLite 등) | 개발 중에 쓰는 도구입니다. 세션 끝나면 버려도 되는 데이터에 스키마 관리를 들일 이유가 없습니다 |
| JUnit / pytest | 각 언어의 기본 도구로 충분하고, "외부 의존성 0" 원칙과 충돌합니다 |
| ELK 같은 로그 수집 | 애초에 목표가 아닙니다. 기기에서, 개발 단계에서 쓰는 도구입니다 |

## 6. 검증 구조

```
        Java 라이브러리 ──만든다──> 한 줄 ──> Python 파서 ──> 필드 비교
```

이 저장소에서 가장 중요한 검사입니다. 이유는 이렇습니다.

직접 손으로 쓴 테스트 데이터에는 **같은 오해가 양쪽에 들어갈 수 있습니다.** 제가 형식을
잘못 이해한 채로 테스트 데이터를 만들면 그 테스트는 통과합니다. 두 구현이 서로를
검사해야 그 오해가 드러납니다.

기대값은 라이브러리 출력을 되읽어서 만들지 않고, 입력값에서 따로 계산합니다.
그리고 이 검사가 실제로 문제를 잡는지도 **일부러 망가뜨려서** 확인했습니다
(구분자 깨뜨리기 / 필드 값에 공백 넣기 / 잘림 표시 지우기 → 셋 다 걸렸습니다).

| 명령 | 무엇을 검사하나 | 방법 |
|---|---|---|
| `make test-viewer` | 파서, 집계, 설정, 서버 API | Python `unittest`, 테스트 데이터 + 실제 HTTP 호출 |
| `make test-lib` | 값 정리, 마스킹, 길이 자르기, 형식, 레벨, 출력 | 직접 만든 테스트 (한글·이모지를 여러 길이 제한에서) |
| `make test-android` | `lib/android` 컴파일 | Android SDK의 `android.jar`로 실제 컴파일 |
| `make roundtrip` | **형식 자체** | Java가 만들고 Python이 읽어서 대조 |
| `make demo` | 전 구간 연결 | 진짜 라이브러리 → 파일 → 뷰어 |

## 7. 성능과 한계

| 항목 | 값 |
|---|---|
| 서버 링버퍼 | 기본 20,000줄 (`bufferSize`). 넘으면 오래된 것부터 버림 |
| 분석 대상 범위 | 링버퍼 전체. 그 이전 기록은 없음 |
| SSE 묶음 주기 | 100ms |
| 브라우저별 큐 | 2,000건. 넘치면 오래된 것부터 버림 |
| 브라우저 보관 / 화면 표시 | 20,000줄 보관 / 최근 1,500줄만 그림 |
| 파싱 비용 | 줄당 정규식 최대 4회. 스레드 하나로 초당 수만 줄 수준 |

**알고 감수한 한계**

- **저장하지 않습니다.** 뷰어를 끄면 버퍼가 사라집니다. 오래 보관하는 건 라이브러리의
  파일 저장 기능이 맡고, 세션을 파일로 저장하는 건 나중 과제입니다.
- **분석은 버퍼 범위 안에서만 됩니다.** "어제 대비 성공률" 같은 건 못 합니다.
  그건 서버 수집 파이프라인이 할 일이고, 애초에 목표가 아닙니다.
- **`flowId`가 없으면 단계별 이탈은 근사값입니다.** 흐름을 잇는 ID는 처음부터 넣어야 합니다.
- **기기 하나만 봅니다.** 여러 대를 동시에 보려면 프로그램을 여러 개 띄우면 됩니다.
- **난독화된 스택 복원(retrace)은 없습니다.** 나중 과제입니다.

## 8. 기능을 추가할 때 손댈 곳

| 하고 싶은 것 | 손댈 곳 |
|---|---|
| 새로운 출력 대상 (크래시 리포터 등) | `Sink` 구현 하나 추가 → `LogLens.addSink()` |
| 새로운 로그 입력 (iOS, 서버 로그, 저장된 세션) | `LogSource` 구현 하나 추가 → `sources/__init__.py`의 `build()` |
| 프로젝트별 탭·이슈 규칙 | **코드 수정 없음.** `config.json`만 교체 |
| 새로운 이슈 종류 | `config.json`의 `issueRules`에 규칙 추가 |
| 새로운 분석 지표 | `analytics.py`의 `aggregate()` + 화면에 카드 하나 |
| 마스킹할 키 추가 | `new Masker().plus("deviceSerial", ...)`를 `LogLens.init()`에 넘김 |

## 9. 처음 붙일 때 (0 → 1)

아직 라이브러리를 안 쓰는 프로젝트에 붙이는 실제 순서입니다.

**① 지금 로그가 어떤지부터 봅니다 — 설정 파일 자동 생성**

```bash
loglens --source adb --package com.your.app --init your-app.json
```

기기의 최근 logcat을 읽어서, **대상 앱이 찍은 태그만** 골라내고 이름이 비슷한 것끼리
묶어서 탭 초안을 만듭니다 (`ChatListFragment`와 `Chats`는 한 탭으로).
**태그 이름과 개수만 읽습니다 — 로그 내용은 집계에도 결과물에도 쓰지 않습니다.**

이미 라이브러리를 쓰는 도메인이 있으면 그건 도메인 탭이 되고, 아직인 것은
예전 태그 패턴 탭이 됩니다.

**② 붙여서 봅니다**

```bash
loglens --source adb --package com.your.app --config your-app.json
```

아직 형식에 맞는 로그는 0%입니다. 지금은 "탭이 달린 logcat"이고, 그게 정상입니다.
**뷰어의 값어치는 로그가 형식을 지킬 때 생깁니다.**

**③ 흐름 하나를 통째로 옮깁니다** (호출부 하나가 아니라)

```java
// 전
Log.d("ChatListFragment", "send fail, room=" + room + " " + e.getMessage());

// 후
LogLens.e(AppDomain.CHAT, "SEND_FAIL", e, "room", room);
```

옮긴 줄부터 도메인 칩, 필드 칩, 이슈 목록에 들어갑니다. 하지만 **성공률 차트가 나오려면
성공과 실패가 짝으로** 있어야 하고, 단계별 이탈은 흐름 전체에 `flowId`가 필요합니다.
그래서 여기저기 한 줄씩 옮기지 말고 **흐름 하나를 골라 끝까지** 옮기는 게 낫습니다.
거기서 처음으로 일반 뷰어가 못 하는 화면이 나옵니다 (§11).

**옛날 로그는 반드시 지웁니다.** 새 로그를 추가만 하고 옛것을 안 지우면 지저분한 로그와
정리된 로그가 같이 남아서 오히려 두 배가 됩니다.

**④ 탭의 `domains`를 채웁니다**

예전 태그 패턴은 그대로 두고 `domains`에 새 도메인을 넣으면, 옮긴 줄과 아직인 줄이
**같은 탭에서 나란히** 보입니다. 얼마나 옮겼는지가 눈에 보입니다.

**⑤ 형식이 자리 잡으면 단계별 이탈을 설정합니다**

`flowId`를 심고 `config.json`의 `funnels`에 단계를 나열하면 화면에 이탈률이 나옵니다.

## 10. 이 도구가 요구하는 것

앞의 절들은 *어떻게 도는가*였습니다. 이 절은 **언제 값을 못 내는가**입니다.
설계상 가장 큰 위험 요소라서 따로 뒀습니다.

### 기능별로 필요한 것

| 기능 | 필요한 것 | 앱을 안 고쳐도? |
|---|---|:--:|
| 레벨 · 검색 · 정규식 필터 | 없음 | ✅ |
| 앱만 보기, 도메인 탭 | 없음 | ✅ |
| 크래시 · ANR · 네이티브 이슈 묶기 | 없음 — 시스템 로그를 읽습니다 | ✅ |
| 도메인 / 이벤트 빈도 | 형식에 맞는 로그 | ❌ |
| 성공률 | 이벤트 이름을 `_OK` / `_FAIL`로 통일 | ❌ |
| 실패 사유 분포 | 실패 로그에 `reason=` / `err=` | ❌ |
| 단계별 이탈 | 흐름 전체에 `flowId=` + 단계 정의 | ❌ |

**✅ 세 줄만으로는 Android Studio Logcat을 이길 수 없습니다.**
차별점은 전부 ❌ 쪽에 있고, 전부 형식에 의존합니다.

### 언제부터 쓸모가 있나

```
 값
  │                                    ┌────  단계별 이탈
  │                          ┌─────────┘
  │                ┌─────────┘               성공률 · 실패 사유
  │      ┌─────────┘
  │──────┘                                   칩 · 검색 · 이슈 묶기
  └──────┬─────────┬──────────┬─────────────────────────
       안 고침    호출부      흐름 하나        도메인 전체
                  1곳         전부
                             ↑ 여기부터
```

기획서에는 "호출부 하나만 바꿔도 가치가 있다"고 적었는데, **실제보다 낙관적입니다.**
한 줄 바꾸면 색깔 있는 칩 하나가 생기는 정도입니다. 성공률은 성공과 실패 이벤트가
**짝으로** 있어야 나오고, 단계별 이탈은 흐름 **전체**에 `flowId`가 있어야 나옵니다.

**실질적인 최소 단위는 호출부 하나가 아니라 "흐름 하나 전체"입니다.**
옮길 계획을 세운다면 "여기저기 한 줄씩"이 아니라 **"흐름 하나를 골라 끝까지"**가 맞습니다.

### 그래서 이건 무슨 도구인가

지저분한 로그를 알아서 정리해 주는 도구가 아닙니다.
**형식을 지키면 그만큼 돌려받게 만드는 도구**입니다.

형식을 안 지킨 로그도 사라지지 않고 그냥 분석에서만 빠집니다(§4.4).
벌을 주는 게 아니라 차이를 만드는 쪽이고, 그 차이가 형식을 지킬 이유가 됩니다.
OpenTelemetry나 Sentry, 구조화 로깅 전반이 같은 성질입니다. 넣은 만큼 나옵니다.

### 이 의존을 줄이는 방법 두 가지 (아직 안 만듦)

**① 뷰어 쪽에서 예전 로그를 뜯어내기.** 방법은 이미 코드에 있습니다. 크래시 이슈 묶기는
앱을 안 고쳤는데도 동작하는데, `config.json`의 정규식으로 원문에서 예외 클래스 이름을
뽑아내기 때문입니다. 이 방식을 이슈 목록이 아니라 **레코드 자체**에 적용하면
(예전 태그 + 패턴 → 도메인/이벤트/필드) 앱을 한 줄도 안 고치고 분석 화면이 켜집니다.

다만 이 방법은 약합니다. 개발자가 로그 문자열을 바꾸면 규칙이 조용히 깨지는데,
그게 바로 이 프로젝트가 벗어나려던 문제입니다. 그래서 이건 **중간 단계로만** 쓸 만합니다.
값을 먼저 보여주고 그다음에 옮기자고 설득하는 순서를 만드는 용도입니다.

**② 자동 변환 도구.** `Log.d(TAG, "...")`를 기계적으로 바꿔 주는 스크립트입니다.
옮기는 비용이 사람 손이 아니라 스크립트가 되면 "해야 하나 말아야 하나" 논쟁 자체가
없어집니다. 근본적인 해법입니다.

# 구현 결정 기록

[기획서](../기획서.md)는 설계 의도를 담는다. 이 문서는 **그걸 실제로 만들면서
초안과 달라진 것 / 초안이 말하지 않아 내가 정한 것**만 기록한다.
기획서를 고쳐 쓰지 않고 따로 두는 이유는, 초안이 무엇을 예측했고 무엇을 놓쳤는지가
그 자체로 기록할 가치가 있어서다.

---

## D1. 초안의 파서 정규식은 틀렸다 — 접두사와 본문을 분리

**초안:**
```
^(?:(?<time>\d{4}-\d\d-\d\d ...) )?(?<level>[VDIWE])/<PREFIX>_(?<domain>[A-Z]+)...
```

**문제:** `\d{4}-\d\d-\d\d` 는 연도를 요구하는데, `adb logcat` 의 표준 포맷들
(`brief`, `time`, `threadtime`)은 **연도를 찍지 않는다**. 초안의 `time` 그룹은
사실 파일 싱크의 포맷이다 — 그건 우리가 소유하니까 연도가 있는 게 맞다.
두 소스의 접두사를 하나의 옵셔널 그룹으로 합치려 한 게 실수였다.

**결정:** 얇은 **접두사 파서 3종**(threadtime / brief·time / filesink) + 공용
**본문 파서 1개**. 접두사는 소스마다 다르고, 계약인 것은 본문뿐이다.

**부수 효과:** adb 호출 시 `-v threadtime` 을 **명시적으로 고정**한다. 포맷을
사용자 환경 기본값에 맡기면 파서가 조용히 깨진다.

## D2. 도메인 문자 집합을 넓혔다

초안의 `[A-Z]+` 는 `FILE_XFER`, `API2` 같은 지극히 평범한 도메인을 거부한다.
→ `[A-Z0-9_]+`.

## D3. `<PREFIX>` 는 config 에서 오므로 정규식 이스케이프

초안은 `<PREFIX>` 를 정규식에 그대로 끼워 넣었다. prefix 는 사용자 config 값이라
정규식 메타문자가 들어올 수 있다. `re.escape` 후 삽입한다. (테스트 있음)

## D4. 빈 값 센티널 `-`

초안의 문법에서 값은 `\S+` 라 `k=` 는 매치되지 않는다. 그런데 `null`/`""` 을
넘기는 call site 는 반드시 생긴다. 그 한 번에 레코드 전체가 강등되면 안 되므로
emitter 가 `-` 로 바꾼다.

## D5. 잘림은 UTF-8 **코드포인트 경계**에서

초안은 "4KB 근처 잘림 대비, 초과분은 통째로 자르고 `...[cut]`" 까지만 말한다.
한글은 UTF-8 3바이트, 이모지는 4바이트(서로게이트 페어)다. 바이트로 자르면
문자가 반으로 갈려 mojibake 나 디코딩 실패가 난다. `Truncator` 는 바이트로 세고
코드포인트로 자른다. (한글·이모지 각각 여러 한도에서 테스트)

## D6. 개행이 공백보다 위험하다

초안은 "값에 공백/구분자 없음"만 말한다. 실제 파서 킬러는 **개행**이다 —
한 줄 = 한 레코드가 깨지면 그 뒤가 전부 어긋난다. `Sanitizer` 는 값과 메시지
**양쪽에서** `\n`/`\r`/`\t` 를 리터럴 이스케이프로 바꾼다. 공백·`|` 는 값에서만 잡는다.

## D7. 파서는 관용적, emitter 는 엄격 — 줄 끝 공백

**실제로 당한 버그.** 합성 생성기가 필드 뒤에 공백 한 칸을 남겼고, 그것 때문에
`UPLOAD_DONE` 레코드가 전부 unstructured 로 강등돼서 대시보드의 FILE_XFER
성공률이 **0%** 로 나왔다. 로그는 멀쩡해 보였고 숫자만 틀렸다 — 제일 나쁜 종류의 버그다.

두 군데를 고쳤다: 생성기(원인)와 파서(`body.rstrip()`, 방어).
공백 한 칸에 레코드를 버릴 이유가 없다.

## D8. 릴리스 게이팅 기본값은 "디버그 아님"

`LogLens.init()` 을 부르기 전 `debug = false`. 초기화를 잊었을 때 V/D 가
**새는** 것보다 **조용히 빠지는** 쪽이 안전하다. 안전한 방향으로 실패한다.

## D9. core 를 순수 자바로 (Kotlin 아님) — **D21 에서 뒤집힘**

기획서 §10 은 "Kotlin 우선"을 로드맵에 뒀고, §5 의 인터페이스 예시는 자바였다.
core 를 안드로이드·서드파티 무의존 순수 자바로 두면:

- 일반 JVM 에서 `javac` 만으로 컴파일·테스트된다 (JUnit 조차 없이)
- **뷰어 파서와의 왕복 검증**을 실제로 돌릴 수 있다 ← 이게 결정적이었다
- `minSdk 21`, 자바 앱에서도 그대로 쓰인다

Kotlin DSL 은 core 위에 얹는 얇은 레이어로 남겨둔다 (로드맵).

## D10. 이슈 규칙은 예외 **클래스명이 있는 줄만** 잡는다

처음 규칙(`"FATAL EXCEPTION|Exception|Error"`)은 크래시 하나를 이슈 여러 개로
쪼갰다: `FATAL EXCEPTION: main` 줄이 `UnknownCrash` 로, 실제 예외 줄이
`IllegalStateException` 으로 따로 잡혔다. 이슈 트레이의 존재 이유가 "그룹핑"인데
그걸 스스로 어긴 셈이다.

→ `[\w.$]+(?:Exception|Error)\b` — 클래스명처럼 생긴 토큰이 있는 줄만.
(회귀 테스트 있음: 헤더나 `at ...` 프레임이 별도 이슈로 새면 실패한다)

## D11. 퍼널은 flowId 가 있으면 흐름 단위, 없으면 카운트 근사

기획서 §9-5 가 "상관 ID 는 초기에 결정"이라고 경고한 그 지점이다. 뷰어는
`flowId` 필드가 있으면 흐름 단위로 이탈률을 내고, 없으면 단순 카운트로 근사한
뒤 **어느 모드인지 UI 에 표시한다**. 근사값을 정확한 값인 척하지 않는다.

## D12. 규칙 `when` 의 속성은 화이트리스트

config 의 이슈 규칙이 임의 속성명을 검사하면 오타가 조용히 "매치 안 됨"이 된다.
허용 속성 목록을 두고, 벗어나면 **로딩 시점에 예외**를 던진다. 조용한 실패보다 낫다.

## D13. 뷰어는 표준 라이브러리만 쓴다

의존성 0. 이유: `pip install` 없이 파일 복사만으로도 돌고, PyInstaller 단일
바이너리 패키징이 쉬워지고, 사내 네트워크 제약이 있는 환경에서도 붙는다.
SSE 서버는 `http.server.ThreadingHTTPServer` 로 충분하다.

## D14. 소스를 추상화했다 (adb / file / synth)

초안은 adb 만 상정한다. 소스를 인터페이스 뒤로 빼면:

- **기기 없이** 뷰어 전체를 개발·테스트·데모할 수 있다 (`--source synth`)
- 로드맵의 `.session` 저장/재생이 붙을 이음매가 이미 생긴다 (`--source file`)
- 재연결 로직이 adb 소스 안에 갇힌다 — 상위 레이어는 끊김을 몰라도 된다

## D15. SSE 는 헤더보다 먼저 구독한다

원래 순서는 `헤더 전송 → subscribe()` 였다. 그러면 클라이언트가 헤더를 받은 시점과
서버 쪽 구독이 성립하는 시점 사이에 들어온 레코드를 **조용히 놓친다**. 브라우저는
아무 에러도 못 보고 그냥 몇 줄이 비는데, 사람 눈으로는 절대 안 잡힌다.
API 테스트를 쓰다가 이 경합에 걸려서 발견했다. → `subscribe()` 를 헤더보다 앞으로.

## D16. pid 필터는 클라이언트 쪽 토글, 이슈 필터에는 양보

pid 추적은 만들어 놓고 **어디에도 적용하지 않은 채** README 에 기능으로 적혀 있었다
(리뷰에서 지적받아 발견). 붙이면서 정한 것:

- **서버 ingest 단이 아니라 UI 토글**로. 버퍼에서 아예 빼버리면 이슈 트레이가 망가진다.
- **이슈 필터가 켜져 있으면 pid 필터를 적용하지 않는다.** ANR 은 앱이 아니라
  `ActivityManager`(system_server pid)가 찍는다. pid 로 거르면 방금 클릭한 이슈가
  화면에서 사라진다 — 사용자는 뷰어가 고장 났다고 생각할 것이다.
- pid 를 모르는 소스(file/synth)에서는 토글 자체를 숨긴다. 아무것도 안 하는
  체크박스는 없느니만 못하다.

## D17. `make demo` 는 실제로 깨져 있었다

`--out build/demo/app-2026-08-12.log` 를 주면 `FileSink` 가 거기에 날짜를 **또** 붙여서
`app-2026-08-12-2026-08-12.log` 를 만든다. 뷰어는 없는 파일을 열고 조용히 아무것도
스트리밍하지 않았다. 테스트 296개가 전부 초록이었는데도 못 잡았다 —
**어떤 테스트도 make 타깃을 실행하지 않았기 때문**이다.

→ `--out` 에는 접두사만 주고, 뷰어에는 날짜가 붙은 실제 경로를 준다.
그리고 `test -f` 가드를 넣어 파일이 없으면 조용히 넘어가지 않고 실패하게 했다.

교훈: README 의 헤드라인 명령은 테스트 커버리지 밖에 있기 쉽다.

## D18. config 를 손으로 쓰게 하지 않는다

실제 사내 앱에 붙여보고 나서 추가했다. 붙여봤더니 **구조화 0%** 였고 — 당연하다,
아직 라이브러리를 안 심었으니 — 그 상태에서 사용자가 할 수 있는 일이 없었다.
도메인이 뭔지 모르는데 도메인 탭을 적으라고 하는 꼴이었다.

`--init` 은 실제 로그를 표본으로 읽어 config 초안을 만든다. 핵심은 세 가지:

- **pid 필터가 결정적이다.** 대상 앱 pid 로 거르면 시스템/타앱 태그 140여 종이
  한 번에 사라지고 앱이 찍은 태그 여덟 개만 남는다. 이 신호 없이는 쓸모가 없다.
- **태그 이름으로 군집화한다.** 접미사(Fragment/Task/Manager…)를 떼고 단수·복수를
  합친다. 안 그러면 `Chats` 와 `ChatListFragment` 가 다른 탭이 되어 탭이 무의미해진다.
- **태그 이름과 빈도만 읽는다.** 메시지 본문은 집계에도 산출물에도 쓰지 않는다.
  로그 본문에는 PII 가 있을 수 있고, config 는 저장소에 커밋되는 파일이다. 테스트로 강제.

**여기서도 버그를 하나 밟았다.** `adb logcat -d` 는 링버퍼의 **가장 오래된 줄부터** 준다.
표본을 앞에서 N줄 자르니 부팅 직후 로그만 보게 됐고, 앱 태그가 하나도 안 잡혔다.
→ `-t N` (최근 N줄)으로 교체.

## D19. minSdk 21 을 선언했으면 21에서 도는지 확인해야 한다

`ThreadLocal.withInitial()` 을 쓰고 있었다. 자바 8 API 라 `source/target 1.8` 이면
될 것 같지만, **안드로이드에서는 API 26 부터** 존재한다. minSdk 21 을 선언해 놓고
그걸 쓰면 API 21~25 기기에서 클래스 로딩 시점에 `NoSuchMethodError` 로 죽는다.
파일 싱크를 켠 앱만, 구형 기기에서만 죽는다 — 최악의 재현 조건이다.

→ 익명 서브클래스(`new ThreadLocal<T>(){ initialValue() }`)로 교체. 어디서나 된다.

교훈: "자바 8 문법"과 "안드로이드가 제공하는 자바 8 API"는 다른 이야기다.
문법(람다·default 메서드)은 D8 이 디슈가링해 주지만, **런타임 API 는 안 해준다**
(core library desugaring 을 따로 켜지 않는 한).

이 김에 `make test-android` 를 추가했다 — Android SDK 의 `android.jar` 를 찾아
`lib/android` 를 실제로 컴파일한다. 없으면 건너뛴다.

## D20. "call site #1 부터 가치"는 낙관적이었다 — 포지셔닝 수정

리뷰에서 받은 질문: *"결국 규칙대로 로그를 찍은 프로젝트에 붙였을 때만 제대로
쓸 수 있는 것 아니냐."* **맞다.** 방어하지 않고 문서를 고쳤다.

**무엇이 무엇을 요구하는가**

| 기능 | 통합 0줄로? |
|---|:--:|
| 레벨·검색·정규식 필터, pid 필터, 탭 라우팅 | ✅ |
| 크래시·ANR·네이티브 이슈 그룹핑 (시스템 로그 파싱) | ✅ |
| 도메인/이벤트 빈도, 성공률, 실패사유, 퍼널 | ❌ |

✅ 쪽만으로는 Android Studio Logcat 을 이길 수 없다. **차별점은 전부 ❌ 쪽이고,
전부 규칙에 의존한다.**

**가치 곡선의 무릎.** 기획서 §11 의 "call site #1 부터 가치"는 실제 동작보다
낙관적이다. 한 줄을 옮기면 색칠된 칩 하나를 얻을 뿐이다. 성공률은 성공·실패
이벤트가 **쌍으로** 있어야 뜨고, 퍼널은 흐름 **전체**에 `flowId` 가 박혀야 뜬다.
실질적 최소 단위는 call site 하나가 아니라 **"한 흐름 전체"** 다.

강등 사다리(§06)가 없애는 것은 *들어오는 문턱*이지 *분석 기능*이 아니다.
둘을 같은 문장에 뭉뚱그린 게 초안의 오류였다.

**그래서 이건 무엇인가.** 지저분한 로그를 고쳐 주는 도구가 아니라,
**규율을 지키면 그게 보상으로 돌아오게 만드는 도구**다. 규칙을 어긴 로그는
사라지지 않고 분석에서만 빠진다 — 벌이 아니라 비대칭이고, 그 비대칭이 채택 유인이다.
같은 성질이 OpenTelemetry·Sentry·구조화 로깅 전반에 있다.

**의존을 줄이는 두 갈래 (미구현, 기록만).**

1. **파서 쪽 필드 추출** — 메커니즘은 이미 있다. 크래시 이슈 그룹핑은 통합 0줄인데도
   config 정규식으로 원문에서 예외 클래스명을 뽑는다. 이 추출을 이슈 트레이 말고
   레코드 자체에 적용하면(레거시 태그 + 패턴 → 도메인/이벤트/필드) 앱을 안 고치고
   대시보드가 켜진다. **취약하다** — 로그 문자열이 바뀌면 조용히 깨지고, 그게 바로
   이 프로젝트가 벗어나려던 취약함이다. 다리이지 목적지가 아니다.
2. **codemod** — `Log.d(TAG, "...")` 를 기계적으로 변환. 이관 비용이 사람 손이
   아니라 스크립트가 되면 채택 논쟁 자체가 사라진다. 근본책.

**기획서.md 는 고치지 않았다.** 초안이 무엇을 예측했고 무엇을 놓쳤는지가 그 문서의
값어치다. 수정은 여기(D20)와 README·ARCHITECTURE §11 에 있다.

## D21. 전부 Kotlin 으로 — D9 를 뒤집었다

D9 에서 "core 는 순수 자바, Kotlin 은 나중에 얇게 얹는다"고 정했는데 뒤집었다.
이유는 하나가 아니다.

- 안드로이드 라이브러리를 자바로만 내는 건 2026 년 기준으로 낡았다
- gradle 빌드가 붙으면서 "javac 만으로 테스트된다"는 D9 의 근거가 약해졌다
- 무엇보다 **기획서 §5 가 트레이드오프라고 적었던 문제를 Kotlin 이 없앤다**

### 얻은 것: 키-값 짝이 컴파일 시점에 보장된다

기획서는 varargs 방식의 대가로 "컴파일 타임 키-값 짝 안전성 없음"을 적었다.
Kotlin 에서는 이게 사라진다.

```kotlin
LogLens.i(AppDomain.AUTH, "LOGIN_OK", "uid" to uid, "msg" to "성공")
```

인자 개수를 홀수로 쓰는 실수 **자체가 불가능하다.**

### 잃은 것 두 가지 (정직하게)

1. **`.aar` 이 kotlin-stdlib 을 요구한다.** "외부 의존성 0" 이 "1개" 가 됐다.
   실무상 안드로이드 앱은 거의 다 이미 갖고 있어서 체감 비용은 없지만, 사실은 사실이다.
2. **`javac` 만으로 테스트되던 게 gradle 필요로 바뀌었다.** 다만 gradle 은 `.aar`
   때문에 어차피 필요해졌으므로 새로 생긴 부담은 아니다.

### API 를 두 벌 낸 이유

`"uid" to uid` 의 `to` 는 Kotlin 의 infix 문법이다. 자바에는 이런 문법이 없어서,
같은 API 를 자바에서 쓰려면 필드마다 `new Pair<>("uid", uid)` 를 써야 한다.
자바가 대부분인 프로젝트(실제 대상 앱이 자바 781 / 코틀린 25)에서는 마찰이 크다.
기획서 §5 가 "빌더 패턴은 장황해서 기각"한 것과 같은 이유다.

그래서 자바용으로 기존 가변 인자 형태를 그대로 남겼다.

```kotlin
@JvmStatic  fun i(d: LogDomain, event: String, vararg kv: Any?)              // Java + Kotlin
@JvmSynthetic fun i(d: LogDomain, event: String, vararg fields: Pair<...>)   // Kotlin 전용
@JvmStatic  fun i(d: LogDomain, event: String)                               // 인자 없음
```

**설계하기 전에 작은 프로젝트로 먼저 검증했다.** 가변 인자 오버로드가 둘이면 충돌할 수
있어서다. 확인된 것:

- `@JvmSynthetic` 을 붙이면 자바에서 아예 안 보이므로 자바 쪽 충돌이 없다
- 인자가 없을 때는 두 가변 인자 오버로드가 애매해지므로, **인자 없는 오버로드를 따로**
  둬야 한다 (가장 구체적이라 항상 이긴다)
- Kotlin 에서 `"uid" to 1` 은 Pair 쪽으로, `"uid", 1` 은 Any? 쪽으로 정확히 간다

### 이 변환이 형식을 깨뜨리지 않았다는 증거

**양쪽 대조 검증(§왕복)이 그대로 통과했다.** 언어를 바꿨는데 뷰어 파서는 손대지
않았고, 28개 케이스가 전부 통과한다. Kotlin 의 Pair API 로 만든 줄과 자바식
가변 인자로 만든 줄이 **같은 줄인지**도 케이스로 넣었다.

이게 두 컴포넌트를 형식으로만 묶어 둔 설계의 값어치다.
한쪽을 통째로 다른 언어로 다시 써도 반대쪽은 아무것도 몰라도 된다.

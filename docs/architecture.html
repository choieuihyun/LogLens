뷰어와 분석은 찍힌 로그만큼만 좋아진다. 아무리 좋은 뷰어도 잡다한 로그 위에선 잡다하게 보인다. 그래서 진짜 레버리지는 뷰어가 아니라 로그를 규격대로 찍게 만드는 쪽에 있고, 뷰어는 그 규격을 착취하는 소비 도구다.

이 판단이 구조를 결정했다. 컴포넌트는 둘인데, 둘 사이에 코드 의존이 없다. 공유하는 건 가운데의 한 줄 텍스트 규격뿐이다. 라이브러리를 코틀린으로 다시 쓰든 뷰어를 Go 로 옮기든 반대쪽은 알 필요가 없다.

01계약 — 한 줄이 전부다

emitter 와 뷰어가 공유하는 유일한 것. 이 줄의 어느 부분이 계약이고 어느 부분이 아닌지를 구분하는 게 설계의 첫 단추였다.

불변식 넷

  • 태그 = <PREFIX>_<DOMAIN> — 도메인을 본문에 넣는 흔한 래퍼(Log.d("APP", "[AUTH] …"))는 그 순간 logcat 태그 필터를 무력화한다. 태그 자리에 두면 도메인 필터가 공짜다.
  • 한 줄 = 한 레코드. 여러 줄로 쪼개면 멀티스레드 환경에서 다른 스레드 로그가 사이에 끼어 복구가 불가능해진다.
  • 값에 공백·|·개행 없음. 개행이 진짜 파서 킬러다.
  • 파서는 예외를 던지지 않는다. 규격 위반은 실패가 아니라 강등이다.
2026-08-12 11:41:24.930 I/APP_AUTH: evt=TOKEN_ISSUE flowId=f9254 token=*** expiresIn=3600 authType=oauth2 ↑ 가려짐 ↑ 안 가려짐

token 은 가려졌고 authType 은 안 가려졌다. 마스킹이 정확 키 매칭이어야 하는 이유다 — 부분 일치로 가리면 auth 가 authType 까지 먹어치우고, 그러면 개발자가 마스킹을 우회하기 시작한다. 그게 진짜 사고로 이어진다.

03emitter — 단계 순서에 이유가 있다

// call site 가 보는 전부 LogLens.i(AppDomain.AUTH, "LOGIN_OK", "uid", uid, "msg", "로그인 성공"); LogLens.e(AppDomain.NET, "SOCKET_FAIL", e, "host", host);
  1. 01레벨 게이팅 맨 앞이어야 한다. 릴리스에서 d() 는 varargs 배열 하나만 만들고 즉시 반환한다 — 문자열 연결도, 정화도, 마스킹도 없다. 로깅 표준이 성능 때문에 거부당하는 걸 막는 가장 값싼 방법.
  2. 02포맷 · 정화 키 검증, 값에서 공백→_, |→/, 개행→리터럴 이스케이프. 빈 값은 센티널 - — k= 는 문법 위반이라 레코드 전체를 강등시킨다.
  3. 03마스킹 정화 뒤에 오는 이유: 마스킹 결과(***)도 공백 없는 토큰이어야 계약이 유지된다. 순서가 반대면 마스킹 산출물을 다시 검사해야 한다.
  4. 04절단 맨 마지막. 필드를 다 붙인 뒤의 최종 길이라야 의미가 있다. 바이트로 세고 코드포인트로 자른다 — 한글 3바이트, 이모지 4바이트라 순진하게 바이트로 자르면 문자가 반으로 갈린다.
  5. 05싱크 팬아웃 logcat · 파일 · (향후) 크래시 리포터. 싱크가 던진 예외는 삼킨다 — 로깅이 앱을 죽이면 안 된다.

도메인은 앱이 공급한다

이게 "어느 프로젝트에나 붙는다"의 전부다. 도메인 목록은 프로젝트의 정체성이라 라이브러리에 enum 으로 박는 순간 재사용이 끝난다.

// 라이브러리 — 도메인을 모른다
public interface LogDomain { String tag(); }

// 앱 — 자기 도메인을 정의한다
public enum AppDomain implements LogDomain {
    AUTH, CHAT, NET, FILE_XFER;
    public String tag() { return "APP_" + name(); }
}
모듈 경계

lib/core 는 안드로이드를 모른다. 순수 자바다. 덕분에 일반 JVM 에서 javac 만으로 테스트되고, 뷰어 파서와의 왕복 검증(§08)을 실제로 돌릴 수 있다. 이게 결정적이었다.

함정 — 실제로 밟음

라이브러리 모듈의 BuildConfig.DEBUG 는 그 라이브러리의 빌드타입이라, 앱이 release 여도 true 일 수 있다. 릴리스 앱에서 V/D 로그가 통째로 샌다.

→ 앱이 init(isDebug) 로 주입하거나 FLAG_DEBUGGABLE 을 런타임에 읽는다. 초기화 전 기본값은 디버그 아님 — 잊었을 때 새는 것보다 빠지는 게 안전하다.

04뷰어가 기기에 붙는 원리

웹 GUI 를 원하는데 브라우저 샌드박스는 USB·adb 소켓·임의 프로세스 실행을 막는다. WebUSB 로도 안 된다 — adb 서버가 이미 기기를 독점하고 있다.

adb 서브프로세스에서 의도적으로 고정한 것 넷

고정값안 하면
-v threadtimeadb 기본 포맷은 버전·환경마다 다르다. 어느 날 남의 PC 에서 파서가 조용히 깨진다.
errors="replace"기기가 깨진 바이트를 뱉으면 스트림 전체가 죽는다. 한 줄 손상은 감수하고 파이프라인은 돌린다.
bufsize=14KB 블록이 찰 때까지 로그가 안 나온다. "버튼 누르면 바로 뜬다"가 이 도구의 존재 이유다.
pidof 재확인앱이 재시작되면 pid 가 바뀐다. 연결할 때마다 다시 푼다.
pid 필터가 결정적이다

실제 사내 앱에 붙여보니, 대상 앱 pid 로 거르는 것만으로 시스템·타앱 태그 140여 종이 한 번에 사라지고 앱이 찍은 태그 여덟 개만 남았다. 이 신호 없이는 화면이 쓸모가 없다.

단, 이슈를 클릭한 상태에서는 pid 필터를 양보한다. ANR 은 앱이 아니라 ActivityManager(system_server)가 찍기 때문에, pid 로 거르면 방금 클릭한 이슈가 화면에서 사라진다.

재연결은 예외가 아니라 정상 동작

기기 sleep, USB 재연결, 앱 재시작, adb kill-server. 스트림은 끊긴다. 이걸 상위 레이어가 알게 하면 모든 레이어가 재연결을 알아야 한다.

그래서 소스가 무한 제너레이터다. 소비자는 그냥 for line in source.lines() 이고 끊김을 모른다. 상태 변화는 --------- loglens: … 마커 줄로 흘려보낸다 — 파서가 RAW 로 처리하고 Hub 가 가로채 UI 상태줄로 올린다. 별도 채널이 필요 없다.

같은 인터페이스 뒤에 소스가 셋 있다. 이 이음매 덕분에 기기 없이 뷰어 전체를 개발·테스트·데모할 수 있고, 로드맵의 세션 저장/재생이 붙을 자리도 이미 있다.

05뷰어 내부 — 스레드와 백프레셔

파이썬 프로세스 (단일)
│
├── Reader 스레드 (1개)
│     for line in source.lines():
│         hub.ingest(parser.parse(line))
│
├── Hub  (공유 상태, threading.Lock)
│     ├── deque(maxlen=20000)   링버퍼
│     ├── IssueTray             규칙별·그룹키별 카운터
│     └── [Queue, Queue, ...]   구독자별 큐 (브라우저 탭 하나당 하나)
│
└── ThreadingHTTPServer
      ├── GET /api/stream  → 장수명. 큐를 빨아 SSE 로 밀어냄
      └── 그 외            → 단명. JSON / 정적 파일

파서가 단일 스레드인 게 중요하다. 로그는 초당 수천 줄이 올 수 있지만 정규식 매칭은 싸고, 순서 보존이 중요하다. 병렬화하면 순서가 깨지고 얻는 게 없다.

백프레셔 정책: 느린 구독자를 굶긴다

for q in subscribers:
    try:    q.put_nowait(payload)
    except Full:
        q.get_nowait()      # ← 가장 오래된 걸 버리고 새 걸 넣는다
        q.put_nowait(payload)

백그라운드 탭이나 멈춘 브라우저 때문에 전체 파이프라인이 막히면 안 된다. 로그 뷰어에서 오래된 줄을 잃는 건 감수할 만한 손실이고, 실시간성이 막히는 건 아니다.

경합 — API 테스트를 쓰다가 발견

원래 순서는 헤더 전송 → subscribe() 였다. 그러면 클라이언트가 헤더를 받은 시점과 구독 성립 시점 사이의 레코드를 조용히 놓친다. 브라우저는 아무 에러도 못 보고 그냥 몇 줄이 빈다 — 사람 눈으로는 절대 안 잡힌다.

→ subscribe() 를 헤더보다 앞으로.

집계 — 구조화 로그라서 가능한 것

범용 logcat 뷰어가 원리상 못 하는 게 이거다. 문자열밖에 없으면 group-by 할 키가 없다. 우리는 emitter 단에서 이미 키-값으로 쪼개 놨으니 그냥 세면 된다.

  • 성공률 — 이벤트 접미사 _OK / _FAIL 로 판정
  • 실패 사유 분포 — reason·err·code 필드에서 추출
  • 퍼널 이탈 — flowId 로 흐름을 묶고, 없으면 카운트로 근사하되 어느 모드인지 UI 에 표시한다. 근사값을 정확한 값인 척하지 않는다

06강등 사다리 — 점진 도입의 기술적 기반

"전부 이관해야 쓸 수 있다"는 요구가 없으니 채택 장벽이 사라진다. 탭은 domains 와 legacyTagPattern 을 둘 다 가질 수 있어서, 이관된 줄과 아직인 줄이 같은 탭에 나란히 보인다 — 이관 진행도가 눈에 보인다.

08검증 구조 — 왕복이 핵심이다

손으로 쓴 픽스처는 양쪽에 같은 오해를 심을 수 있다. 내가 파서를 잘못 이해한 채로 픽스처를 쓰면 픽스처 테스트는 통과한다. 두 구현이 서로를 검사해야 그 오해가 드러난다.

Java Formatter ──생성──▶ 한 줄 ──▶ Python Parser ──▶ 필드 대조 (emitter) (viewer)

기대값은 Formatter 의 출력을 되읽어 만들지 않는다 — 입력으로부터 독립적으로 조립한다. 그리고 이 검사가 실제로 파손을 잡는지 음성 대조로 확인했다: 구분자 파손 · 필드에 공백 주입 · 잘림 표식 제거 → 셋 다 검출됐다.

make test-lib242 단언정화·마스킹·절단·포맷·게이팅·싱크 (한글·이모지를 여러 절단 한도에서)

테스트가 못 잡은 것

make demo 가 깨져 있었다. --out 에 날짜 붙은 경로를 주면 파일 싱크가 날짜를 또 붙여서 뷰어는 없는 파일을 열고 조용히 아무것도 스트리밍하지 않았다. 335개 검사가 전부 초록인데도 못 잡았다 — 어떤 테스트도 make 타깃을 실행하지 않았기 때문이다.

README 의 헤드라인 명령은 테스트 커버리지 밖에 있기 쉽다.

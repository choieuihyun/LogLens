로그가 지저분하면 아무리 좋은 뷰어를 써도 지저분하게 보입니다. 그래서 이 프로젝트는 뷰어보다 로그를 정해진 형식으로 찍게 만드는 쪽에 더 무게를 뒀습니다. 뷰어는 그 형식을 활용해서 필터링하고 집계하는 쪽입니다.

이 판단이 구조를 결정했습니다. 컴포넌트는 둘인데 서로의 코드를 전혀 참조하지 않습니다. 공유하는 건 가운데의 로그 한 줄 형식뿐입니다. 라이브러리를 코틀린으로 다시 쓰든 뷰어를 Go 로 옮기든 반대쪽은 알 필요가 없습니다.

01로그 한 줄의 형식

라이브러리와 뷰어가 공유하는 유일한 것입니다. 이 줄의 어느 부분이 약속이고 어느 부분이 아닌지를 구분하는 게 설계의 첫 단추였습니다.

반드시 지켜야 하는 규칙 네 가지

  • 태그는 <접두사>_<도메인> — 도메인을 본문에 적는 방식(Log.d("APP", "[AUTH] …"))은 모든 로그의 태그를 APP 하나로 만들어서 logcat 태그 필터를 무의미하게 만듭니다. 태그 자리에 두면 도메인 필터가 공짜로 따라옵니다.
  • 로그 한 줄이 레코드 하나. 여러 줄로 쪼개면 멀티스레드 환경에서 다른 스레드 로그가 사이에 끼어 복구할 방법이 없습니다.
  • 값에 공백, |, 줄바꿈이 안 들어갑니다. 줄바꿈이 특히 파서를 깨뜨립니다.
  • 파서는 예외를 던지지 않습니다. 형식에 안 맞는 줄은 버리는 게 아니라 등급을 낮춥니다.
2026-08-12 11:41:24.930 I/APP_AUTH: evt=TOKEN_ISSUE flowId=f9254 token=*** expiresIn=3600 authType=oauth2 ↑ 가려짐 ↑ 안 가려짐

token 은 가려졌고 authType 은 그대로입니다. 민감한 값을 가릴 때 키 이름이 정확히 일치할 때만 가리기 때문입니다. auth 가 들어간 키를 전부 가리는 식으로 만들면 authType 같은 멀쩡한 필드까지 안 보이게 되고, 그러면 개발자가 마스킹을 우회하기 시작합니다.

03로깅 라이브러리 — 처리 순서에 이유가 있다

// 호출부가 쓰는 전부 LogLens.i(AppDomain.AUTH, "LOGIN_OK", "uid", uid, "msg", "로그인 성공"); LogLens.e(AppDomain.NET, "SOCKET_FAIL", e, "host", host);
  1. 01레벨 확인 맨 앞이어야 합니다. 릴리스 빌드에서 d() 를 부르면 인자 배열 하나만 만들고 바로 돌아옵니다 — 문자열을 잇지도, 값을 정리하지도, 마스킹하지도 않습니다. 로깅 표준이 "느려진다"는 이유로 거부당하는 걸 막는 가장 싼 방법입니다.
  2. 02문자열 조립 · 값 정리 키가 규칙에 맞는지 확인하고, 값에서 공백은 _ 로, | 는 / 로, 줄바꿈은 문자 두 개로 바꿉니다. 값이 비면 - 를 넣습니다 — k= 는 형식 위반이라 그 줄 전체가 등급이 낮아집니다.
  3. 03마스킹 값 정리 뒤에 오는 이유: 마스킹 결과인 *** 도 공백 없는 한 덩어리여야 형식이 유지됩니다. 순서가 반대면 마스킹 결과를 다시 검사해야 합니다.
  4. 04길이 자르기 맨 마지막입니다. 필드를 다 붙인 뒤의 최종 길이라야 의미가 있습니다. 바이트 수로 세되 글자 단위로 끊습니다 — 한글은 3바이트, 이모지는 4바이트라 바이트 위치로 그냥 자르면 글자가 반으로 갈려 깨집니다.
  5. 05출력 대상에 전달 logcat, 파일, 나중엔 크래시 리포터까지. 출력 중에 예외가 나면 삼킵니다 — 로그 때문에 앱이 죽으면 안 되니까요.

도메인 목록은 앱이 정합니다

이게 "어느 프로젝트에나 붙는다"의 핵심입니다. 도메인 목록은 프로젝트마다 다른데, 라이브러리 안에 enum 으로 박아 넣으면 그 순간 다른 프로젝트에서 못 씁니다.

// 라이브러리 — 도메인이 뭔지 모릅니다
public interface LogDomain { String tag(); }

// 앱 — 자기 도메인을 정의합니다
public enum AppDomain implements LogDomain {
    AUTH, CHAT, NET, FILE_XFER;
    public String tag() { return "APP_" + name(); }
}
모듈 경계

lib/core 는 안드로이드를 전혀 참조하지 않습니다. 순수 자바입니다. 덕분에 일반 JVM 에서 javac 만으로 테스트할 수 있고, 뷰어 파서와 서로 대조하는 검증(§08)도 실제로 돌릴 수 있습니다. 이게 컸습니다.

함정 — 실제로 밟음

라이브러리 모듈의 BuildConfig.DEBUG 는 그 라이브러리의 빌드 타입이라, 앱을 release 로 빌드해도 true 로 남을 수 있습니다. 그러면 릴리스 앱에서 V/D 로그가 전부 새어 나갑니다.

→ 앱이 init(isDebug) 로 직접 알려주거나, FLAG_DEBUGGABLE 을 실행 중에 읽습니다. 초기화 전 기본값은 디버그 아님입니다. 깜빡했을 때 로그가 새는 것보다 안 찍히는 게 안전하니까요.

04뷰어가 기기에 붙는 방법

웹 화면으로 보고 싶은데, 브라우저 보안 정책이 USB·adb 소켓·프로그램 실행을 전부 막습니다. WebUSB 라는 게 있지만 안드로이드 ADB 인터페이스에는 접근할 수 없고, 애초에 adb 서버가 이미 기기를 독점하고 있습니다.

adb 를 실행할 때 일부러 고정한 것 네 가지

고정값안 하면
-v threadtimeadb 기본 형식은 버전·환경마다 다릅니다. 기본값에 맡기면 어느 날 다른 사람 PC 에서 파서가 조용히 깨집니다.
errors="replace"기기가 깨진 바이트를 내보내도 스트림이 죽으면 안 됩니다. 한 줄 망가지는 건 감수하고 나머지는 계속 읽습니다.
bufsize=14KB 가 찰 때까지 로그가 안 나옵니다. "버튼 누르면 바로 뜬다"가 이 도구를 만든 이유입니다.
pidof 재확인앱을 재시작하면 프로세스 ID 가 바뀝니다. 연결할 때마다 다시 찾습니다.
앱 ID 필터가 결정적입니다

실제 사내 앱에 붙여 봤더니, 대상 앱 ID 로 거르는 것만으로 시스템·다른 앱 태그 140여 종이 한 번에 사라지고 그 앱이 찍은 태그 여덟 개만 남았습니다. 이 필터가 없으면 화면이 쓸모가 없습니다.

다만 이슈를 클릭해서 보는 중에는 이 필터를 끕니다. ANR 은 앱이 아니라 ActivityManager(시스템 프로세스)가 찍기 때문에, 앱 ID 로 거르면 방금 클릭한 이슈가 화면에서 사라집니다.

재연결은 예외 상황이 아니라 평소 동작입니다

기기가 잠들거나, USB 를 다시 꽂거나, 앱을 재시작하거나, adb kill-server 를 하면 스트림이 끊깁니다. 이걸 위쪽 코드가 알게 하면 모든 계층이 재연결을 처리해야 합니다.

그래서 로그를 읽는 쪽을 끝나지 않는 반복문으로 만들었습니다. 쓰는 쪽은 그냥 for line in source.lines() 이고 끊김을 모릅니다. 상태 변화는 --------- loglens: … 같은 특별한 줄로 흘려보냅니다 — 파서는 이걸 형식에 안 맞는 줄로 처리하고, Hub 가 가로채서 화면 상태 표시줄에 올립니다. 별도 통로를 만들 필요가 없습니다.

로그를 어디서 읽을지가 같은 인터페이스 뒤에 셋 있습니다. 덕분에 기기 없이 뷰어 전체를 개발하고 테스트하고 시연할 수 있고, 나중에 세션 저장/재생을 붙일 자리도 이미 있습니다.

소스쓰임
adb실제 기기. 재연결·앱 추적·형식 고정
file저장해 둔 로그 재생 / tail -f
synth가짜 로그 생성 — 기기 없이 데모, CI 테스트

05뷰어 내부 — 스레드 구성

파이썬 프로세스 (단일)
│
├── 읽기 스레드 (1개)
│     for line in source.lines():
│         hub.ingest(parser.parse(line))
│
├── Hub  (공유 상태, threading.Lock)
│     ├── deque(maxlen=20000)   링버퍼 (꽉 차면 오래된 것부터 밀려남)
│     ├── IssueTray             규칙별·묶음별 카운터
│     └── [Queue, Queue, ...]   브라우저 탭마다 큐 하나
│
└── ThreadingHTTPServer
      ├── GET /api/stream  → 오래 살아있음. 큐에서 꺼내 브라우저로 밀어냄
      └── 그 외            → 금방 끝남. JSON / 정적 파일

파싱을 스레드 하나에서만 하는 게 중요합니다. 로그는 초당 수천 줄이 올 수 있지만 정규식 매칭 자체는 싸고, 순서가 유지되는 게 더 중요합니다. 병렬로 돌리면 순서가 깨지는데 얻는 건 없습니다.

브라우저가 못 따라올 때

for q in subscribers:
    try:    q.put_nowait(payload)
    except Full:
        q.get_nowait()      # ← 가장 오래된 걸 버리고 새 걸 넣습니다
        q.put_nowait(payload)

못 따라오는 탭은 오래된 로그를 잃습니다. 의도한 동작입니다. 백그라운드에 있거나 멈춘 탭 하나 때문에 전체가 막히면 안 되니까요. 로그 뷰어에서 오래된 줄 몇 개를 잃는 건 감수할 만하지만, 실시간이 막히는 건 그렇지 않습니다.

브라우저로 밀어주는 방식 (SSE)

결정값이유
배치 주기100 ms줄마다 보내면 초당 수천 개 이벤트가 발생해 브라우저가 버티지 못합니다. 사람 눈에 100ms 는 즉시로 느껴집니다.
하트비트15 s아무것도 안 오가면 중간 프록시나 브라우저가 연결을 끊어 버리는 걸 막습니다.
구독자 큐2,000넘치면 가장 오래된 것부터 버립니다.
재연결브라우저EventSource 가 알아서 다시 붙습니다. 서버는 상태 표시만 바꿉니다.
타이밍 문제 — API 테스트를 쓰다가 발견

원래 순서는 응답 헤더 전송 → 구독 등록 이었습니다. 그러면 브라우저가 헤더를 받은 시점과 서버에 구독이 등록된 시점 사이에 들어온 로그를 조용히 놓칩니다. 브라우저에는 에러도 안 뜨고 그냥 몇 줄이 비는데, 사람 눈으로는 절대 못 잡습니다.

→ 구독 등록을 헤더보다 앞으로 옮겼습니다.

집계 — 형식을 지켜야 가능한 것

일반 logcat 뷰어가 이걸 못 하는 이유는 간단합니다. 문자열밖에 없으면 무엇을 기준으로 묶을지가 없습니다. 우리는 로그를 찍을 때 이미 키-값으로 쪼개 놨으니 그냥 세면 됩니다.

  • 성공률 — 이벤트 이름 끝이 _OK 인지 _FAIL 인지로 판정
  • 실패 사유 분포 — reason·err·code 필드에서 꺼냄
  • 단계별 이탈 — flowId 로 같은 흐름끼리 묶고, 없으면 개수로 근사하되 어느 방식인지 화면에 표시합니다. 근사값을 정확한 값처럼 보여주지 않습니다

06형식에 안 맞는 줄도 버리지 않습니다

탭은 domains 와 legacyTagPattern 을 둘 다 가질 수 있어서, 옮긴 줄과 아직인 줄이 같은 탭에 나란히 보입니다 — 얼마나 옮겼는지가 눈에 보입니다.

과장하지 않기

"시작하는 문턱이 없다"와 "호출부 하나만 바꿔도 값이 나온다"는 다른 이야기입니다. 이 3단계 구조는 문턱을 없애 줄 뿐, 분석 기능을 켜 주지는 않습니다. 실제로 쓸모가 생기는 건 흐름 하나를 전부 옮겼을 때입니다 — §11 참고.

08검증 — 양쪽을 서로 대조합니다

직접 손으로 쓴 테스트 데이터에는 같은 오해가 양쪽에 들어갈 수 있습니다. 제가 형식을 잘못 이해한 채로 테스트 데이터를 만들면 그 테스트는 통과합니다. 두 구현이 서로를 검사해야 그 오해가 드러납니다.

Java 라이브러리 ──만든다──▶ 한 줄 ──▶ Python 파서 ──▶ 필드 비교

기대값은 라이브러리 출력을 되읽어서 만들지 않고, 입력값에서 따로 계산합니다. 그래야 비교에 의미가 있습니다. 이 검사가 실제로 문제를 잡는지도 일부러 망가뜨려서 확인했습니다: 구분자 깨뜨리기 · 값에 공백 넣기 · 잘림 표시 지우기 → 셋 다 걸렸습니다.

11이 도구가 요구하는 것

앞의 절들은 어떻게 도는가였습니다. 이 절은 언제 값을 못 내는가입니다. 설계상 가장 큰 위험 요소라서 따로 뒀습니다.

기능필요 조건앱을 안 고쳐도?

가능 세 줄만으로는 Android Studio Logcat 을 이길 수 없습니다. 차별점은 전부 불가 쪽에 있고, 전부 형식에 의존합니다.

언제부터 쓸모가 있나

기획서에는 "호출부 하나만 바꿔도 가치가 있다"고 적었는데, 실제보다 낙관적입니다. 한 줄 바꾸면 색깔 있는 칩 하나가 생기는 정도입니다. 실질적인 최소 단위는 호출부 하나가 아니라 "흐름 하나 전체"입니다. 옮길 계획을 세운다면 "여기저기 한 줄씩"이 아니라 "흐름 하나를 골라 끝까지"가 맞습니다.

그래서 이건 무슨 도구인가

솔직한 위치

지저분한 로그를 알아서 정리해 주는 도구가 아닙니다. 형식을 지키면 그만큼 돌려받게 만드는 도구입니다.

형식을 안 지킨 로그도 사라지지는 않고 그냥 분석에서만 빠집니다(§06). 벌을 주는 게 아니라 차이를 만드는 쪽이고, 그 차이가 형식을 지킬 이유가 됩니다. OpenTelemetry 나 Sentry 도 같은 성질입니다. 넣은 만큼 나옵니다.

이 의존을 줄이는 방법 두 가지 아직 안 만듦

① 뷰어 쪽에서 예전 로그를 뜯어내기. 방법은 이미 코드에 있습니다 — 크래시 이슈 묶기는 앱을 안 고쳤는데도 동작하는데, 설정의 정규식으로 원문에서 예외 클래스 이름을 뽑아내기 때문입니다. 이 방식을 이슈 목록이 아니라 레코드 자체에 적용하면(예전 태그 + 패턴 → 도메인/이벤트/필드) 앱을 한 줄도 안 고치고 분석 화면이 켜집니다.

다만 약합니다. 로그 문자열이 바뀌면 규칙이 조용히 깨지는데, 그게 바로 이 프로젝트가 벗어나려던 문제입니다. 중간 단계로만 쓸 만합니다 — 값을 먼저 보여주고 그다음에 옮기자고 설득하는 순서를 만드는 용도입니다.

② 자동 변환 도구. Log.d(TAG, "…") 를 기계적으로 바꿔 주는 스크립트입니다. 옮기는 비용이 사람 손이 아니라 스크립트가 되면 "해야 하나 말아야 하나" 논쟁 자체가 없어집니다. 근본적인 해법입니다.
